Architecture UI et Interaction

L'interface utilisateur d'HybeliorWorld repose sur le framework CommonUI d'Epic, avec des widgets activables héritant de UHWCommonActivatableWidget (gamepad-friendly, gestion stack et focus). Le HUD principal AHWHUD est un HUD 2D Canvas custom (pas un widget UMG) qui héberge le floating damage et le canvas de cooldowns. Les widgets gameplay (Inventaire, Dialogue, Skill Bar, Quest Tracker, Nameplate, Map) s'ajoutent par-dessus en UMG.

Le système d'Enhanced Input de UE5.4 (jamais legacy) gère 28 Input Actions, 2 Input Mapping Contexts (clavier/souris + manette), 2 PlayerMappableInputConfigs (remapping joueur), et un DataAsset UHWInputConfig qui mappe les UInputAction vers des FGameplayTag pour le routage GAS. Les interactables du monde partagent le contrat IInteractable (Containers, Doors, Supply Pods) ou utilisent un canal séparé (Portals avec auto-overlap).

HUD principal AHWHUD — HUD Canvas 2D custom. Floating damage avec 4 catégories (dégâts normal/critique, soin normal/critique), animations curve-driven (scale, speed, alpha). HUDStatLIVE_RepCounter répliqué pour pousser les refresh stats sans répliquer chaque attribut.
Framework UI CommonUI — UHWCommonActivatableWidget (base navigable gamepad), stack de widgets, gestion focus, support multi-plateforme. Préfixes BP variables : WBP_, UI_, UW_, BP_ selon l'époque.
Enhanced Input 28 Input Actions · 2 Input Mapping Contexts (KBM / Gamepad) · UHWInputConfig (DataAsset, mapping IA ↔ Gameplay Tags) · UHWInputComponent (extends UEnhancedInputComponent, déclaré DefaultInputComponentClass).
Settings UHWSettingsLocal — préférences joueur persistées : sensibilité souris/manette, remapping touches, configuration des raccourcis personnalisés. Persistance entre sessions.
Interactables du monde Interface IInteractable commune (Interact(), GetInteractableGUID(), SetInteractableGUID()) implémentée par AHWContainer, AHWDoor, ASupplyPod. AHWPortal dérive directement AActor (auto-overlap, design intentionnel). ADynamicContentManager spawne depuis DataTable.
Widgets gameplay 23 widgets recensés — HUD (ResourceBars, AbilityCooldowns, Nameplates, Map, FloatingDamage), Inventaire (CommonInventoryList, EquipmentWidget, MenuTabs), Dialogue, Skill Bar (10 slots), Quest Tracker (5 quêtes max), Login (UI_Login, UI_Register, UI_CreateCharacter), CombatStateIcon, CustomButton.
Persistance interactables FastArrayed sur AHWPlayerController — FHWContainerMaster (containers ouverts) + FHWSupplyPodMaster (pods ouverts), répliqués COND_OwnerOnly, sérialisés en JSON via OWS clés "ContainersOpened" + "SupplyPodsOpened".

Enhanced Input · UHWInputConfig + UHWInputComponent

28 IA · 2 IMC · routage natif + GAS via Tags
Pipeline d'input — du clavier au GAS

Chaque appui parcourt une chaîne en 5 étapes : périphérique physique → UInputMappingContext (résolution touche → InputAction) → UInputAction (IA_Move, IA_Jump, IA_Weapon_Right, etc.) → UHWInputConfig (mapping UInputAction ↔ FGameplayTag InputTag.*) → UHWInputComponent qui dispatche en deux canaux parallèles :

Canal natif via BindNativeAction() → méthode C++ sur AHWGASPlayerCharacter (effet immédiat : combo, animation locale). Canal GAS via BindAbilityActions() → callbacks AbilityInputTagPressed / AbilityInputTagReleased sur l'ASC (activation des abilities, dégâts, cooldowns). Certaines actions (par ex. IA_Weapon_Right) existent dans les deux canaux : le natif gère la frappe immédiate, le GAS gère l'ability sous-jacente.

UHWInputConfig (DataAsset) 2 tableaux : NativeInputActions (TArray<FHWInputAction> pour le canal C++) · AbilityInputActions (TArray<FHWInputAction> pour le canal GAS). Chaque FHWInputAction = UInputAction* + FGameplayTag InputTag. Lookup via FindNativeInputActionForTag() / FindAbilityInputActionForTag() avec log d'erreur si tag manquant.
UHWInputComponent Extends UEnhancedInputComponent. Déclaré DefaultInputComponentClass dans DefaultInput.ini. Templates clés : BindNativeAction() (binding C++ natif) · BindAbilityActions() (binding GAS, retourne handles dans BindHandles pour RemoveBinds au logout) · AddInputMappings() / RemoveInputMappings() (registre les UPlayerMappableInputConfig dans le subsystem Enhanced Input du LocalPlayer).
28 Input Actions Mouvement (Move, Sprint, Dash, Dodge, Jump, Crouch, WalkRun) · Vol (Flying, FlyingUp, FlyingDown) · Combat (ReadyToFight, Weapon_Left, Weapon_Right, NormalAbility1/2, SpecialAbility1) · Caméra (Look_Mouse, Look_Stick, ChangeCamera, MouseWheelUp/Down) · Cible (Target, NextTarget, PreviousTarget) · UI (OpenInventory, OpenMainMenu, ShowMap, Interact).
2 Input Mapping Contexts IMC_Default_KBM (clavier + souris) · IMC_Default_Gamepad (manette). Priorité de contexte distincte : gameplay, UI, dialogue, véhicule. Support du remapping en jeu via UHWSettingsLocal.
2 PlayerMappableInputConfigs PMI_Default_KBM + PMI_Default_Gamepad dans /Game/Input/Configs/. Configurations remappables exposées au joueur. Note : l'API PlayerMappableInputConfig est marquée deprecated en UE5.4 — migration vers la nouvelle API recommandée (dette connue).
InputData_Player (HWInputConfig) Asset UHWInputConfig principal du projet, situé dans /Game/Input/. Référencé par AHWGASPlayerCharacter::SetupPlayerInputComponent() pour brancher tous les bindings au démarrage.
Tags d'input — déclaration C++ centralisée

Tous les InputTags sont déclarés en C++ natif dans FHWGameplayTags (Source/HybeliorWorld/Public/AbilitySystem/HWGameplayTags.h). Hiérarchie principale : InputTag_Move, InputTag_Look_Mouse, InputTag_Look_Stick, InputTag_Jump_Triggered/_Completed, InputTag_Sprint, InputTag_Crouch, InputTag_Dash, InputTag_ChangeCamera, InputTag_Target/_NextTarget/_PreviousTarget, InputTag_Weapon_Left/_Right, InputTag_Flying/_FlyingUp/_FlyingDown, InputTag_MouseWheelUp/_Down, InputTag_SwitchWeapon, InputTag_Interact, InputTag_WalkRun, InputTag_Abilities_* (WeaponLeft, WeaponRight, Dash, NormalAbility1/2, SpecialAbility1, ReadyToFight).

— Flux end-to-end : exemple d'attaque à droite —

1. Joueur appuie LMB (KBM) ou RT (Gamepad)
2. IMC résout vers IA_Weapon_Right
3. UHWInputComponent (UEnhancedInputComponent) émet ETriggerEvent::Started
4a. [Native] InputTag_Weapon_Right → Input_WeaponRight() → animation/combo C++ immédiat
4b. [GAS] InputTag_Abilities_WeaponRight → AbilityInputTagPressed(tag) → ASC active GA_WeaponRight
5. Au relâchement (Completed) → AbilityInputTagReleased(tag) → ASC notifie l'ability active

HUD principal · AHWHUD

Canvas 2D · floating damage · stat refresh répliqué
AHWHUD — HUD custom Canvas 2D (pas UMG)

Le HUD principal AHWHUD hérite de AHUD et utilise DrawHUD() pour rendre directement sur le Canvas 2D. Il n'est pas un widget UMG. Il héberge le système de floating damage (textes flottants au-dessus des cibles) et le canvas de cooldowns rapide. Les widgets UMG (Inventaire, Dialogue, Skill Bar, etc.) sont ajoutés par-dessus via AddToViewport.

BP associé : BP_HUD dans /Game/Game/. Note connue : les cooldowns d'Ability1 sont hardcodés au niveau HUD (incohérence — devrait être générique via le SkillBarComponent).

FHWFloatingDamage Struct runtime — texte, alpha, scale, position, flags IsCritical / IsHealing. Aucun object pool : chaque hit alloue un nouveau struct (dette connue, pression GC sur 60+ mobs simultanés).
Animation curves 3 courbes : FloatingDamageScaleCurve (pop-then-shrink) · FloatingDamageSpeedCurve (vitesse verticale) · FloatingDamageTextAlphaCurve (fade out).
4 catégories visuelles Dégâts normaux · Dégâts critiques · Soin normal · Soin critique. Chacune a sa fonte (FloatingDamageFont, FloatingCriticalDamageFont, FloatingHealingFont, FloatingCriticalHealingFont), couleurs (FloatingDamageFontColor, DropShadowColor, OutlineColor) et durée min d'affichage.
AddFloatingDamageItem() Méthode principale — (FString DamageText, AActor* DamagedActor, FVector2D InitialDisplayLocationOffset, bool IsHealing, bool IsCritical, bool ShowDropShadow, bool ShowOutline).
HUDStatLIVE_RepCounter Compteur int32 répliqué (ReplicatedUsing=OnRep_HUDStatLIVEChanged) sur AHWPlayerController. Incrémenté serveur via IncrementHUDStatLIVE(). Le RepNotify déclenche le refresh client de tous les widgets stats (canon : pousser un signal de changement plutôt que de répliquer chaque attribut individuellement).
Hit Flash (complémentaire) Feedback Niagara côté acteur (par-dessus le mesh) qui vient s'ajouter au floating damage Canvas du HUD. Voir doc VFX Audio Rendu/Hit Flash.

Widgets gameplay · Inventaire, Dialogue, Skill Bar, Quest, Login

UMG · UHWCommonActivatableWidget · stack-aware
Pattern commun — composant ↔ widget par delegates

Les widgets gameplay suivent un pattern uniforme : un composant joueur (sur AHWGASPlayerCharacter ou AHWPlayerController) détient l'état runtime et expose des multicast delegates ; le widget UMG se branche dans NativeConstruct et se débranche dans NativeDestruct. Ce pattern unifie Inventaire (UHWInventoryComponent), Dialogue (UHWDialogueComponent), Skill Bar (UHWSkillBarComponent), Quest Tracker (UHWQuestComponent), HUD (HUDStatLIVE).

UHWCommonInventoryListWidget Grille d'inventaire — 4 items par ligne, filtre par type d'item. Composante ListView désactivée temporairement en C++ (référence InventoryComponent conservée). BP : WBP_Inventory. Inventaire · Grille
UHWEquipmentWidget Paperdoll 16 slots pour les items équipés. Drag-and-drop depuis l'inventaire. SlotMap = TMap<EEquipmentSlot, UBorder*>. BP : WBP_Equipment / BP_Equipment. Équipement · 16 slots
UHWInventoryEntry Tile individuelle — icône + quantité + tooltip au survol. Right-click menu non implémenté (incohérence connue). Tile · Tooltip
UHWMenuTabsWidget Onglets du menu principal — SetActiveTab(), QuitToMenu(), QuitGame(), PlayFadeIn() / PlayFadeOut(). Toggled par AHWPlayerController::ToggleMainMenu() (HWPlayerController.h:549) et ToggleMap() (HWPlayerController.h:553). Menu · Tabs
UHWDialogueWidget Affichage du dialogue actif. Bind delegates OnDialogueNodeChanged + OnDialogueEnded de UHWDialogueComponent. Méthodes : ShowDialogueNode(SpeakerName, Text, Choices) · OnChoiceSelected(ChoiceIndex). Speaker name + body text + liste verticale de choix. Dialogue · Choix

Interactables · IInteractable + IInteractable-libres

5 acteurs · contrat unique · persistance OWS
Architecture des interactables

Tous les objets interactifs du monde partagent (ou pas) le contrat IInteractable. 3 implémentent l'interface : AHWContainer (coffres et caisses), AHWDoor (portes de zone OWS), ASupplyPod (capsules à usage unique). 2 utilisent un canal séparé : AHWPortal (auto-overlap, design intentionnel — pas d'IInteractable) et ADynamicContentManager (orchestrateur de spawn depuis DataTable, pas un interactable lui-même).

Méthodes du contrat : Interact() (entry point joueur, corps C++ vide — implémenté en BP) · GetInteractableGUID() (retourne un nouveau GUID à chaque appel par défaut — bug connu, doit retourner un GUID stocké) · SetInteractableGUID(FGuid). Les sous-classes doivent overrider GetInteractableGUID() pour retourner le GUID répliqué stocké.

AHWContainer Coffres et caisses pillables. Propriétés : LootTableID, InteractableGUID (répliqué, OnRep_InteractableGUID), bIsCurrentlyOpen (jamais modifié en C++ — driven serveur via OnRep), UDataTable* ItemDataTable. BlueprintNativeEvents : Interact(), ContainerOpened(), ContainerClosed() (corps C++ vides — BP gère animation + VFX). Flux : Interact → BP → Server_OpenContainer() RPC. BP : BP_Container. Loot · Persistance
AHWDoor Porte interactive avec zone travel OWS. Propriétés : ZoneName, StartingLocation, StartingRotation, InteractableGUID (répliqué, OnRep vide). Méthode TravelThroughDoor(AHWGASPlayerCharacter*) serveur uniquement — validations HasAuthority(), !IsTransferringBetweenZones() (anti-double-trigger), puis SetIsTransferringBetweenZones(true) + StopMovementImmediately() + ShowLoadingScreen() + GetZoneServerToTravelTo() (OWS RPC, stratégie MapWithFewestPlayers). BP : BP_Door, BP_DoorPortal (hybride). Zone Travel · OWS
ASupplyPod Capsule de ravitaillement à usage unique par personnage. Implémente IInteractable avec persistance via FHWSupplyPodMaster (FastArrayed). Une fois ouverte, ajoute le GUID dans la liste persistée du joueur — ne peut plus être ouverte. BP : BP_SupplyPod01. Drop · Unique
AHWPortal Hérite directement AActor — n'implémente pas IInteractable (design intentionnel : auto-overlap). UBoxComponent BoxCollision (100×100×100 défaut, ECC_Pawn Overlap) déclenche OnBoxOverlap() au passage du joueur → TravelThroughPortal(OtherActor) avec validations HasAuthority(), Cast vers AHWGASPlayerCharacter, CapsuleComponent->IsOverlappingActor(this) (validation extra), latch IsTransferringBetweenZones. BP : BP_BoxPortal. Auto-overlap · Travel
ADynamicContentManager Orchestrateur de spawn d'interactables depuis une DataTable. Lit FHWInteractableDataTableRow (InteractableGUID, InteractableTransform, TSubclassOf<AActor> InteractableToSpawn, bIsPlayerInstanced) et instancie au runtime. Permet le peuplement dynamique des zones sans placement manuel dans l'éditeur. BP : HubWorldContentManager, DataTable : DT_InteractablesToSpawn. Spawn · DataTable
— Persistance interactables (FastArray + OWS) —

Sur AHWPlayerController, deux FastArrayed serializers répliqués COND_OwnerOnly tracent l'état d'ouverture côté joueur : FHWSupplyPodMaster (TArray<FHWSupplyPodOpenedItem { FGuid SupplyPodGUID }>) + FHWContainerMaster (TArray<FHWContainerOpenedItem { FGuid ContainerGUID }>).

API exposée : IsSupplyPodOpened(), IsContainerOpened(), AddSupplyPodToOpenedList(), AddContainerToOpenedList(), SerializeSupplyPodsOpened(), LoadSupplyPodsOpenedFromJSON(), RefreshStateOfRelevantSupplyPods(), RefreshStateOfRelevantContainers(). Cycle complet : Player Interact → [Client] Interact() → [Server] Server_OpenContainer / Server_OpenSupplyPod RPC → [Server] AddContainerToOpenedList(GUID) → réplication FastArray → persisté via OWS clés "ContainersOpened" + "SupplyPodsOpened". Bug connu : AHWContainer::IsContainerOpened() appelle par erreur HWPlayerController->IsSupplyPodOpened() au lieu de ->IsContainerOpened() — containers et supply pods partagent la même liste d'état.

Synthèse · cohérence inter-systèmes

UI ↔ Composants joueur ↔ GAS ↔ OWS
Liaisons clés

L'écosystème UI/Interaction d'HybeliorWorld est strictement composant-driven : chaque widget UMG s'abonne aux delegates de son composant joueur (Inventory, Dialogue, Quest, SkillBar) plutôt que d'observer directement le GAS. Les composants centralisent l'état, le GAS gère la logique gameplay, OWS persiste le tout. Pour la chaîne d'input, voir aussi la page Pipeline Ability (étape 5 « Liaison des inputs »). Pour les flux de zone travel, voir Architecture (§ Plugins → OWSPlugin) et Pipeline Quest (clés OWS).
