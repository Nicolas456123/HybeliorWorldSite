Étape 1 — Définir un objet (DataTable)

FHWItemStaticDataStruct · EItemType · EItemSubCategory
Structure de données statiques d'un objet

Chaque objet du jeu est défini dans un DataTable via la structure FHWItemStaticDataStruct. Elle contient l'ensemble des métadonnées nécessaires : nom, description, poids, type, sous-catégorie, taille de stack, niveau requis, durabilité, icône et meshes 3D.

Le type d'objet est défini par EItemType (None, Resource, Weapon, Consumable, Equipment) et affiné par EItemSubCategory qui compte plus de 106 catégories distinctes.

Name / Description Nom et description affichés dans l'interface — texte localisable.
Weight / StackSize Poids unitaire et nombre maximum d'objets empilables dans un seul emplacement d'inventaire.
ItemType (EItemType) Catégorie principale : None, Resource, Weapon, Consumable, Equipment.
SubCategory (EItemSubCategory) Sous-catégorie fine parmi 106+ entrées — permet un filtrage précis dans l'inventaire, le commerce et les conditions de quête.
RequiredLevel / MaxUses / Durability Niveau minimum pour utiliser l'objet, nombre d'utilisations maximales et points de durabilité initiale.
Icon (UTexture2D*) Texture 2D utilisée pour l'affichage dans l'inventaire, les tooltips et les barres d'actions.
StaticMesh / SkeletalMesh Meshes 3D pour la représentation dans le monde (drop au sol) et sur le personnage (équipement porté).
Caracteristics — TArray<FHWCara> Tableau de caractéristiques associées à l'objet. Chaque entrée contient un ECara (MaxHealth, Attack, Defense, CritRate, CritDamage, dégâts/résistances élémentaires, etc.) et une CaraValue numérique. Stats · ECara
16 Equipment Slots De HeadSlot à CrystalSlot, chaque emplacement est mappé par un Order (1 à 16) qui détermine la position dans l'interface d'équipement. Order 1–16

Étape 2 — Table de loot

UHWLootTable · FHWLootEntry · RollLoot
Définition probabiliste du butin

UHWLootTable est un UPrimaryDataAsset qui définit une table de loot complète. Chaque table possède un identifiant unique via FGameplayTag, un tableau d'entrées, un nombre de drops garantis et un plafond de drops maximum.

La méthode RollLoot(PlayerLevel, LuckMultiplier) exécute un système en 3 phases : tirage aléatoire → remplissage garanti → limitation au plafond.

LootTableID (FGameplayTag) Identifiant unique de la table de loot — utilisé pour le référencement depuis les mobs, conteneurs et récompenses de quêtes.
GuaranteedDropCount / MaxDropCount Nombre minimum de drops garantis et nombre maximum d'objets que la table peut produire en un seul tirage.
FHWLootEntry Entrée individuelle de la table : ItemTag, DropChance (0–1), MinQuantity/MaxQuantity, MinPlayerLevel, MinMasteryLevel, RequiredMasteryType, HiddenConditionTag, RarityTag. Probabilité · Conditions
RollLoot — Phase 1 Tirage aléatoire : chaque entrée est évaluée contre sa DropChance multipliée par le LuckMultiplier du joueur. Les entrées dont les conditions ne sont pas remplies sont exclues. Random Roll
RollLoot — Phase 2 Remplissage garanti : si le nombre de drops obtenus est inférieur à GuaranteedDropCount, des entrées supplémentaires sont sélectionnées pour atteindre le minimum. Guaranteed Fill
RollLoot — Phase 3 Limitation au plafond : si le nombre total de drops dépasse MaxDropCount, les entrées excédentaires sont retirées par ordre de priorité décroissante. Cap Enforcement

Étape 3 — Entrée dans le monde

MobDead · AHWContainer · Récompenses
Comment un objet apparaît dans le monde

Les objets entrent dans le monde par trois canaux principaux : le drop de mob à la mort, le contenu de conteneur pré-généré ou dynamique, et les récompenses de quêtes ou ajouts manuels.

Mob Drops AHWGASMobCharacter::MobDead() déclenche le tirage de loot via LootTable->RollLoot(). Les objets obtenus sont mis à disposition du joueur ayant infligé le coup fatal. Kill → Loot
Containers AHWContainer implémente IInteractable et possède un LootTableID, un état bIsCurrentlyOpen et un InteractableGUID pour la persistance. Coffre · Persistance
Récompenses / Manuel Les quêtes et les systèmes de test utilisent AddNewItem() et AddItemToTest() pour injecter directement des objets dans l'inventaire du joueur. Quêtes · Debug

Étape 4 — Interaction joueur

AHWPlayerController · Server_OpenContainer · OWS
Du clic joueur à la récupération d'objet

Le joueur déclenche une interaction via AHWPlayerController::Interact() qui appelle GetOverlappedInteractables() pour détecter les objets interactifs à portée.

Pour un conteneur, le Server_OpenContainer() RPC est envoyé au serveur, qui valide l'accès, crée des FHWContainerOpenedItem et persiste l'état via OWS. L'UI affiche ensuite l'inventaire du conteneur et le joueur peut glisser les objets vers son inventaire.

Interact() Point d'entrée de l'interaction joueur — détecte les IInteractable dans la zone de chevauchement et déclenche l'action appropriée.
GetOverlappedInteractables() Retourne la liste des objets interactifs actuellement à portée du joueur, triés par proximité.
Server_OpenContainer() RPC Appel serveur validé — vérifie la légitimité de l'accès, génère le contenu du conteneur et crée les FHWContainerOpenedItem correspondants.
Persistance OWS L'état du conteneur (ouvert/fermé, contenu restant) est persisté côté serveur via OWS pour garantir la cohérence entre sessions.

Étape 5 — Gestion de l'inventaire

UHWInventoryComponent · FHWInventoryMaster · FFastArraySerializer
Stockage, manipulation et réplication des objets

Le composant UHWInventoryComponent gère l'inventaire via la structure FHWInventoryMaster, qui hérite de FFastArraySerializer pour une réplication réseau optimisée.

Chaque objet en inventaire est représenté par un FHWInventoryItem contenant un GUID unique, un identifiant de type, la quantité, le numéro de slot, l'état de durabilité, les statistiques de combat et l'ordre d'affichage.

FHWInventoryItem Structure runtime d'un objet en inventaire : ItemGUID, ItemTypeID, Quantity, InSlotNumber, NumberOfUsesLeft, Condition.
Stats de combat FlatAttack, FlatDefense, FlatHP, pourcentages, CritRate, CritDamage — stockés directement sur l'item pour un accès rapide.
ItemStats array / Order Tableau de statistiques détaillées et ordre d'affichage dans l'inventaire pour le tri et la présentation UI.
AddNewItem Génère un GUID unique, ajoute l'objet au tableau de l'inventaire, gère le stacking automatique et marque le tableau dirty pour la réplication réseau. Ajout · GUID
MoveItem ServerRPC avec validation côté serveur. Gère le déplacement entre slots, entre inventaires, et la logique complexe de swap d'équipement lorsqu'un slot est déjà occupé. Déplacement · Swap
RemoveItem Retire l'objet du tableau, réordonne les emplacements restants et marque le tableau dirty pour synchroniser la suppression avec le client. Suppression · Reorder

Étape 6 — Équiper un objet

EquipmentInventory · GameplayEffect · AbilitySystemComponent
Application dynamique des statistiques via GAS

Lorsqu'un objet est déplacé vers l'EquipmentInventory, le système détermine le slot approprié via GetSlotFromOrder et GetEquipmentSlotOrders.

ApplyEquipmentStats(EquippedItem) crée un UGameplayEffect dynamique de durée Infinite. Pour chaque FHWCara de l'objet, la fonction CaraToAttribute() convertit l'enum en FGameplayAttribute, puis ajoute un modificateur Additive. L'effet est appliqué via ASC->ApplyGameplayEffectToSelf() et le handle est stocké dans ActiveEquipmentEffects (TMap<FGuid, FActiveGameplayEffectHandle>).

GetSlotFromOrder / GetEquipmentSlotOrders Résout le numéro d'Order (1–16) en slot d'équipement concret — détermine où l'objet sera porté sur le personnage.
ApplyEquipmentStats Crée un GameplayEffect dynamique Infinite, convertit chaque FHWCara en FGameplayAttribute via CaraToAttribute(), applique un modificateur Additive.
ASC->ApplyGameplayEffectToSelf() Applique l'effet sur l'AbilitySystemComponent du personnage — les attributs sont immédiatement mis à jour.
ActiveEquipmentEffects TMap<FGuid, FActiveGameplayEffectHandle> — associe chaque objet équipé à son handle d'effet actif pour un retrait propre.
RemoveEquipmentStats Retire l'effet via le handle stocké — les attributs du personnage retrouvent leurs valeurs de base instantanément.

Étape 7 — Représentation visuelle

AHWGASPlayerCharacter · Mesh Components · Blueprint
L'objet équipé prend forme sur le personnage

AHWGASPlayerCharacter expose des composants de mesh dédiés à chaque pièce d'équipement visible : Sword_Mesh, Shield_Mesh, Bow, Chest, Pants, Cloak, Helms, Boots, Head, Hairstyle, Shoulders.

Un événement Blueprint EquipFunction() reçoit la définition de l'objet et applique le SkeletalMesh correspondant sur le composant approprié.

Order 1 — Head Slot de tête : casques, couronnes, capuches. Appliqué sur le composant Helms. Slot 1
Order 5 — Chest Slot de torse : armures, tuniques, robes. Appliqué sur le composant Chest. Slot 5
Order 10 — HandLeft Main gauche : boucliers, orbes, focus. Appliqué sur le composant Shield_Mesh. Slot 10
Order 11 — HandRight Main droite : épées, haches, bâtons. Appliqué sur le composant Sword_Mesh. Slot 11
Order 14 — Pants Slot de jambes : pantalons, jambières, robes longues. Appliqué sur le composant Pants. Slot 14
Order 15 — Boots Slot de pieds : bottes, sandales, chausses. Appliqué sur le composant Boots. Slot 15

Étape 8 — Persistance

Sérialisation JSON · OWS · FastArraySerializer
Sauvegarde et synchronisation de l'inventaire

L'inventaire est sérialisé en JSON via FJsonObjectConverter::UStructToJsonObjectString appliqué à la structure FHWInventoryMaster. La restauration se fait par LoadInventorySerialize() qui parse le JSON, reconstruit la structure et appelle MarkArrayDirty pour forcer la réplication complète.

La persistance serveur utilise OWSPlayerControllerComponent->AddOrUpdateCustomCharacterData() pour stocker les données d'inventaire dans la base OWS.

SerializeInventory() FJsonObjectConverter::UStructToJsonObjectString(FHWInventoryMaster) — convertit l'intégralité de l'inventaire en chaîne JSON.
LoadInventorySerialize() Parse le JSON sauvegardé, reconstruit FHWInventoryMaster et appelle MarkArrayDirty pour synchroniser l'état avec tous les clients.
PersistInventory() Envoie les données sérialisées vers le backend via OWSPlayerControllerComponent->AddOrUpdateCustomCharacterData().
Réplication réseau FastArraySerializer avec condition COND_OwnerOnly et mode push-based — seul le propriétaire reçoit les mises à jour d'inventaire, optimisant la bande passante. Network · Push
OnRep_Inventory Callback de réplication côté client — déclenche ReloadDisplayItems() pour rafraîchir l'ensemble de l'affichage UI de l'inventaire. Client · Refresh

Étape 9 — Affichage UI

UHWCommonInventoryListWidget · UHWEquipmentWidget · UHWInventoryEntry
Présentation visuelle de l'inventaire et de l'équipement

L'inventaire est affiché dans un UHWCommonInventoryListWidget organisé en grille, où chaque case est un UHWInventoryEntry affichant l'icône, la quantité et les informations de tooltip.

L'écran d'équipement utilise UHWEquipmentWidget avec 16 emplacements de bordure mappés via un SlotMap (TMap<EEquipmentSlot, UBorder*>). La structure FHWInventoryDisplayItem fusionne les données runtime et statiques pour alimenter l'UI de manière unifiée.

UHWCommonInventoryListWidget Widget de grille d'inventaire — instancie un UHWInventoryEntry par objet, gère le layout et le scroll.
UHWEquipmentWidget Interface d'équipement à 16 slots — chaque emplacement est un UBorder* mappé dans le SlotMap par EEquipmentSlot.
UHWInventoryEntry Widget d'entrée individuelle : IconImage, QuantityLabel, tooltip au survol, handlers de clic et de drag-and-drop.
FHWInventoryDisplayItem Structure de présentation combinant les données runtime (quantité, durabilité, GUID) et les données statiques (nom, icône, description) pour l'affichage UI.
