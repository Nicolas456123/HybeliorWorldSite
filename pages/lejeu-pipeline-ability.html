Pipeline d'une Ability

De l'éditeur au joueur · 8 étapes
Guide complet de création d'une Ability

Ce guide détaille le parcours complet d'une ability dans Hybélior World : de la création du Blueprint GameplayAbility dans l'éditeur Unreal jusqu'à son exécution en jeu sur la barre de compétences du joueur.

Chaque étape couvre une couche du Gameplay Ability System étendu par nos classes C++ : définition, configuration des effets, assemblage en DataAsset, octroi au personnage, liaison des inputs, activation, affichage UI et relations de tags.

Étape 1 — Créer un Blueprint GameplayAbility

Classe de base · Policies · Tags
Classe de base UHWGameplayAbility

Toute ability du projet dérive de UHWGameplayAbility (qui étend UGameplayAbility). Cette classe expose les paramètres essentiels : politique d'activation, groupe d'activation, nom de l'ability et comportement de fin de frame.

Les valeurs par défaut du constructeur configurent l'ability en InstancedPerActor, avec une politique réseau LocalPredicted et bServerRespectsRemoteAbilityCancellation à false pour éviter les annulations non autorisées côté client.

ActivationPolicy Détermine quand l'ability s'active : OnInputTriggered (une seule fois à l'appui), WhileInputActive (tant que l'input est maintenu), Passive (toujours active).
ActivationGroup Gère l'exclusivité entre abilities : Independent (aucune restriction), Exclusive_Replaceable (remplacée par une autre exclusive), Exclusive_Blocking (bloque les autres exclusives).
AbilityName / bEndAbilityThisFrame Nom lisible de l'ability pour le debug et l'UI. bEndAbilityThisFrame force la terminaison de l'ability dans la même frame que son activation (utile pour les abilities instantanées).
AbilityTags Tags identifiant cette ability. Utilisés par le système pour le filtrage, le ciblage et les relations entre abilities.
CancelAbilitiesWithTag Tags des abilities qui seront annulées quand cette ability s'active. Exemple : une esquive annule les abilities de type « attaque ».
BlockAbilitiesWithTag Tags des abilities bloquées pendant l'exécution de cette ability. Empêche l'activation simultanée d'abilities incompatibles.
ActivationRequiredTags / ActivationBlockedTags Tags requis sur l'avatar pour activer l'ability (ex : être au sol) et tags qui empêchent l'activation (ex : être étourdi).
UHWGameplayAbility_Dodge Ability d'esquive. Propriétés : Direction (vecteur de déplacement), Strength (force de propulsion), Duration (durée du mouvement), DodgingAnimation (montage d'animation), IFrameGameplayEffect (effet d'invincibilité temporaire). Esquive · iFrames
UHWGameplayAbility_FakeProjectile Ability de projectile non physique. Crée un projectile visuel sans simulation balistique — le hit est déterminé par trace ou prédiction côté serveur. Projectile · Visuel
UHWGameplayAbility_TraceSteps Ability à détection par pas successifs. Effectue un trace à chaque step d'animation pour détecter les cibles, idéal pour les attaques en mouvement et les frappes en chaîne. Trace · Steps

Étape 2 — Créer les GameplayEffects

Cost · Cooldown · Damage · Tags
Effets de gameplay associés

Chaque ability nécessite un ou plusieurs GameplayEffects pour gérer ses coûts de ressources, son temps de recharge et ses effets sur la cible. Ces effets sont des assets Blueprint créés dans l'éditeur et référencés par l'ability.

Le système de tags d'échec d'activation (Ability_ActivateFail_*) permet à l'UI de communiquer au joueur la raison précise pour laquelle une ability ne peut pas s'activer.

Cost Effect Déduit une ressource du UHWCombatAttributeSet : Mana, Stamina ou Energy selon l'ability. Appliqué lors du CommitAbility.
Cooldown Effect Effet de type HasDuration. Octroie un tag de cooldown spécifique à l'ability. Tant que l'effet est actif, l'ability ne peut pas être réactivée.
Damage Effect Modifie l'attribut Health de la cible. Passe par le pipeline de calcul de dégâts (UHWGameplayEffectExecutionCalc) pour intégrer les résistances et les réactions élémentaires.
Ability_ActivateFail_IsDead Tag d'échec signalant que le personnage est mort. L'UI affiche un feedback visuel correspondant.
Ability_ActivateFail_Cooldown Tag d'échec signalant que l'ability est encore en temps de recharge. L'UI peut afficher le temps restant.
Ability_ActivateFail_Cost Tag d'échec signalant que le personnage n'a pas assez de ressources (Mana, Stamina ou Energy) pour activer l'ability.
Ability_ActivateFail_TagsBlocked / _TagsMissing Tags d'échec signalant que des tags bloquants sont présents ou que des tags requis sont absents sur le personnage.

Étape 3 — Assembler un AbilitySet DataAsset

UPrimaryDataAsset · Abilities · Effects · Attributes
UHWGameplayAbilitySet

Le UHWGameplayAbilitySet (dérivé de UPrimaryDataAsset) regroupe en un seul asset tout ce qu'un personnage ou une classe doit recevoir : abilities, effets passifs et ensembles d'attributs.

Les handles générés lors de l'octroi sont stockés dans un FHWAbilitySet_GrantedHandles pour permettre le retrait propre des abilities et effets quand le set est retiré (changement de classe, déséquipement d'arme, etc.).

GrantedGameplayAbilities Tableau de structures contenant : la classe de l'Ability, le AbilityLevel et l'InputTag (FGameplayTag) qui liera cette ability à un input du joueur.
GrantedGameplayEffects Tableau de structures contenant : la classe du GameplayEffect et le EffectLevel. Utilisé pour les effets passifs permanents (régénération, buffs de classe, etc.).
GrantedAttributes Tableau de classes d'AttributeSet à octroyer. Assure que le personnage possède les attributs nécessaires aux abilities et effets du set.
FHWAbilitySet_GrantedHandles Structure de suivi. Stocke tous les FGameplayAbilitySpecHandle, FActiveGameplayEffectHandle et références d'AttributeSet octroyés, permettant leur retrait en une seule opération.

Étape 4 — Octroi au personnage

GiveToAbilitySystem · PossessedBy · DynamicAbilityTags
GiveToAbilitySystem

L'octroi des abilities au personnage se fait lors de la prise de possession par le contrôleur. Le AbilitySystemComponent est initialisé, puis chaque AbilitySet est parcouru pour octroyer ses abilities, effets et attributs.

Le point clé : chaque FGameplayAbilitySpec créée stocke l'InputTag dans ses DynamicAbilityTags, permettant au système d'input de retrouver l'ability correspondante par tag.

AHWGASCharacter::PossessedBy() Point d'entrée sur la classe de base. Appelle InitAbilityActorInfo pour lier l'ASC à l'acteur et à son avatar.
AHWGASPlayerCharacter::PossessedBy() Surcharge joueur. Itère sur le tableau AbilitySets du personnage et appelle GiveToAbilitySystem() pour chaque set.
GiveToAbilitySystem() Crée un FGameplayAbilitySpec pour chaque ability du set, stocke l'InputTag dans les DynamicAbilityTags, et donne la spec à l'ASC. Octroie également les GameplayEffects et les AttributeSets.

Étape 5 — Liaison des inputs

InputConfig · EnhancedInput · Tags
UHWInputConfig et liaison par tags

Le UHWInputConfig (DataAsset) définit deux tableaux : NativeInputActions pour les actions système (mouvement, caméra) et AbilityInputActions pour les actions liées aux abilities. Chaque entrée associe un UInputAction à un FGameplayTag (InputTag).

Lors du setup des inputs, le UHWInputComponent mappe chaque InputAction d'ability vers les callbacks AbilityInputTagPressed et AbilityInputTagReleased, qui transmettent l'InputTag à l'ASC.

UHWInputConfig DataAsset contenant les mappings input. NativeInputActions : actions système sans lien GAS. AbilityInputActions : actions liées à des abilities via InputTag.
SetupPlayerInputComponent() Appelé par AHWGASPlayerCharacter. Lie les inputs via UHWInputComponent en appelant BindAbilityActions.
BindAbilityActions() Parcourt les AbilityInputActions et mappe chaque input vers les callbacks AbilityInputTagPressed (appui) et AbilityInputTagReleased (relâchement).
AbilityInputTagPressed(InputTag) Appelé sur UHWAbilitySystemComponent. Recherche l'ability dont les DynamicAbilityTags contiennent l'InputTag reçu et la marque pour activation.

Étape 6 — Activation

ProcessAbilityInput · CommitAbility · Tasks
Pipeline d'activation

L'activation est orchestrée par ProcessAbilityInput(), appelé chaque frame par l'ASC. Cette méthode vérifie d'abord le tag TAG_Gameplay_AbilityInputBlocked, puis filtre les abilities selon leur ActivationPolicy et tente l'activation.

Une fois activée, l'ability passe par CommitAbility qui valide les tags, applique le coût et le cooldown, puis exécute la logique spécifique via des Ability Tasks asynchrones (PlayMontage, WaitDelay, ApplyRootMotion, etc.).

ProcessAbilityInput() Boucle frame par frame. Vérifie TAG_Gameplay_AbilityInputBlocked. Filtre par policy : OnInputTriggered (une fois), WhileInputActive (maintenu), Passive (toujours).
TryActivateAbility() Tentative d'activation standard. Pour les abilities instantanées, TryActivateAbilityBatchedAndEndInSameFrame() regroupe activation et fin dans la même frame réseau.
ActivateAbility → CommitAbility CommitAbility valide les tags de l'ability, applique le Cost Effect (déduit la ressource) et le Cooldown Effect (lance le temps de recharge).
DoesAbilitySatisfyTagRequirements Vérifie les tags built-in (Required/Blocked) plus les exigences additionnelles définies dans UHWAbilityTagRelationshipMapping via GetAdditionalActivationTagRequirements().
Logique spécifique (Tasks) Après le commit, l'ability exécute sa logique via des tâches asynchrones : PlayMontage, WaitDelay, ApplyRootMotion, traces de détection, application d'effets sur les cibles, etc.

Étape 7 — Barre de compétences (UI)

10 slots · Cooldowns · Delegates
UHWSkillBarComponent

Le composant UHWSkillBarComponent gère 10 slots de compétences. Chaque slot est une structure FHWSkillSlot contenant la référence à l'ability assignée, son tag, son icône, les informations de cooldown, l'état d'activabilité, le coût en ressource et le texte de la touche associée.

Le widget UHWSkillBarWidget s'abonne aux delegates du composant et met à jour l'affichage en temps réel via des événements Blueprint.

FHWSkillSlot Structure d'un slot : AssignedAbility, AbilityTag, Icon, CooldownDuration, CooldownRemaining, bCanActivate, ResourceCost, KeybindText.
AssignAbilityToSlot() Assigne une ability à un slot donné. Met à jour l'icône, le coût et le keybind. Diffuse OnSlotChanged.
ActivateSlot() Active l'ability du slot via ASC->TryActivateAbilityByClass(). Vérifie d'abord que le slot contient une ability et que bCanActivate est true.
TickComponent → UpdateCooldowns() À chaque tick, interroge les effets de cooldown actifs sur l'ASC pour mettre à jour CooldownRemaining de chaque slot.
OnSlotChanged / OnCooldownStarted Delegates multicast. UHWSkillBarWidget s'y abonne pour mettre à jour l'UI : changement d'icône, lancement de l'animation de cooldown, grayout quand bCanActivate est false.

Étape 8 — Relations de tags

TagRelationshipMapping · Règles d'activation
UHWAbilityTagRelationshipMapping

Le UHWAbilityTagRelationshipMapping (DataAsset) contient un TArray<FHWAbilityTagRelationship> qui définit les règles de relations entre abilities sans les coder en dur dans chaque Blueprint.

Ce mapping est appliqué lors de l'initialisation du système via AHWGASPlayerCharacter::AbilitySystemInitialized() qui appelle SetTagRelationshipMapping(). Les règles sont ensuite consultées automatiquement dans DoesAbilitySatisfyTagRequirements().

AbilityTag Le tag de l'ability à laquelle cette règle s'applique. Peut être un tag parent pour affecter toute une catégorie d'abilities.
AbilityTagsToBlock Tags des abilities qui seront bloquées tant que l'ability ciblée est active. Permet de définir des incompatibilités globales.
AbilityTagsToCancel Tags des abilities qui seront immédiatement annulées quand l'ability ciblée s'active.
ActivationRequiredTags / ActivationBlockedTags Tags additionnels requis ou bloquants pour l'activation. Complètent les tags définis directement sur l'ability pour une configuration centralisée.
GetAdditionalActivationTagRequirements() Méthode appelée par DoesAbilitySatisfyTagRequirements() pour fusionner les exigences du mapping avec celles de l'ability elle-même.

Le flux complet d'une ability, de sa création à son exécution en jeu :

Pipeline : Éditeur → Joueur

Blueprint GameplayAbility GameplayEffects (ActivationPolicy, Tags) (Cost, Cooldown, Damage) │ │ └──────────┬───────────────────────────┘ ▼ UHWGameplayAbilitySet (DataAsset) Abilities + Effects + Attributes │ ▼ PossessedBy() → GiveToAbilitySystem() Crée FGameplayAbilitySpec InputTag → DynamicAbilityTags │ ┌──────────┴──────────┐ ▼ ▼ UHWInputConfig UHWAbilityTagRelationshipMapping InputAction→Tag Règles Block/Cancel/Required │ │ ▼ │ BindAbilityActions() │ Pressed/Released→ASC │ │ │ └──────────┬──────────┘ ▼ ProcessAbilityInput() (chaque frame) Vérifie AbilityInputBlocked Filtre par ActivationPolicy │ ▼ TryActivateAbility() ActivateAbility → CommitAbility Valide tags + applique Cost + Cooldown │ ┌──────────┴──────────┐ ▼ ▼ Ability Tasks UHWSkillBarComponent PlayMontage, Traces UpdateCooldowns() ApplyRootMotion OnCooldownStarted Apply Effects → UHWSkillBarWidget

1. Création Blueprint GA + GameplayEffects dans l'éditeur Unreal.
2. Assemblage Regroupement dans un UHWGameplayAbilitySet avec les effets et attributs.
3. Octroi PossessedBy() octroie le set au personnage, stocke les InputTags.
4. Liaison UHWInputConfig lie les touches aux tags, les callbacks transmettent à l'ASC.
5. Activation ProcessAbilityInput() → TryActivateAbility() → CommitAbility() → logique spécifique.
6. UI UHWSkillBarComponent met à jour cooldowns et état en temps réel via delegates.
7. Relations UHWAbilityTagRelationshipMapping applique les règles de blocage/annulation à chaque tentative d'activation.
