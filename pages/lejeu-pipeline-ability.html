Pipeline d'une Ability

De la doc GDD au Blueprint jouable · 8 étapes
Guide complet de création d'une Ability

Ce guide décrit le parcours complet d'une Gameplay Ability dans Hybélior World : depuis sa spécification dans le GDD (tier de skill, palier de Maîtrise requis, type de Voie) jusqu'à son Blueprint GA_* instancié sur la barre de compétences du joueur.

Chaque ability appartient à l'un des 4 tiers de skill canoniques : Basique (palier 2 — Initié), Avancé (palier 3 — Adepte), Expert (palier 4 — Expert) et Signature (palier 5 — Maître, condition cachée). L'architecture GAS qui exécute ces abilities (ASC, AttributeSet, calcul de dégâts) est documentée séparément dans Code : Combat ; le système de combos et de Maîtrise d'arme est détaillé dans Pipeline : Combo.

— Tiers de skill et palier de Maîtrise —

Basique — palier 2 (Initié). ~30 pts Stamina, CD 5 s. Combo 3 coups, première compétence active.

Avancé — palier 3 (Adepte). ~50 pts Stamina, CD 12 s. Finisseur de combo, passif de base. Condition supplémentaire à l'usage.

Expert — palier 4 (Expert). ~80 pts Stamina, CD 25 s. Attaque spéciale, combo 4 coups. Condition supplémentaire à l'usage.

Signature — palier 5 (Maître). ~150 pts Stamina, CD 90 s. Technique signature, skin d'arme, quête secrète. Déblocage par HiddenUnlockCondition (tag Héritage couche 4).

Étape 1 — Créer un Blueprint GameplayAbility

1 / 8 · UHWGameplayAbility · Policies · Tags
Classe de base UHWGameplayAbility

Toute ability du projet dérive de UHWGameplayAbility (qui étend UGameplayAbility du framework GAS). Cette classe expose les paramètres essentiels : politique d'activation, groupe d'exclusivité, nom de l'ability et terminaison de frame.

Les valeurs par défaut du constructeur configurent l'ability en InstancedPerActor, avec une politique réseau LocalPredicted (exécution client immédiate, validation serveur a posteriori) et bServerRespectsRemoteAbilityCancellation = false pour éviter les annulations non autorisées côté client.

EHWAbilityActivationPolicy OnInputTriggered (au press, ex. GA_SwordAttack), WhileInputActive (maintenu, ex. GA_Aiming, GA_Blocking), Passive (toujours active, ex. régénération hors combat).
EHWAbilityActivationGroup Independent (coexiste avec toutes les autres), Exclusive_Replaceable (peut être annulée par une exclusive entrante), Exclusive_Blocking (bloque les autres exclusives). Note : l'enum est déclaré mais le code C++ ne l'enforce pas encore — exclusivité réelle gérée via tags.
InstancingPolicy / NetExecutionPolicy InstancedPerActor + LocalPredicted par défaut. Crucial pour la réactivité réseau : l'ability s'exécute côté client immédiatement, le serveur valide ensuite.
AbilityTags Tags identifiant cette ability (ex. Combat.Skill.Sword.Basic.WhirlSlash). Utilisés par le filtrage, le ciblage et le UHWAbilityTagRelationshipMapping (étape 8).
CancelAbilitiesWithTag / BlockAbilitiesWithTag Tags des abilities annulées à l'activation, ou bloquées pendant l'exécution. Exemple : une esquive annule les abilities Combat.Action.Attack ; GA_SwordAttack bloque elle-même Combat.State.Dead, Combat.State.Frozen.
ActivationRequiredTags / ActivationBlockedTags Tags requis sur l'ASC pour activer (ex. Combat.State.ReadyToFight requis par GA_SwordAttack) et tags qui empêchent l'activation (ex. Combat.State.DodgedRecently bloque GA_BowShoot — anti-exploit).
UHWGameplayAbility_Dodge Esquive directionnelle. Propriétés natives : Direction (0 Avant, 1 Droite, 2 Arrière, 3 Gauche), Strength (500 cm/s pour DodgeBack, 700 pour les trois autres), Duration (0.6 s), DodgingAnimation, IFrameGameplayEffect (invulnérabilité immédiate), DelayDodgedRecentlyApplication (0.25 s avant le tag anti-spam). Esquive · IFrames
UHWGameplayAbility_MovementMode Bascule de mode de locomotion en 3 patterns : Start (applique GE), Stop (retire GE), Toggle (vérifie un tag pour basculer). Utilisée par GA_SprintStart/Stop, GA_Crouch, GA_FlyingStart/Stop, GA_SwimmingStart/Stop, etc. Locomotion · 3 modes
UHWGameplayAbility_ToggleState Bascule générique pilotée par tag : si StateTag présent → retire les effets associés ; sinon → applique le GE. Utilisée pour GA_ReadyToFight, GA_Aiming, GA_Blocking. Toggle · Tag
UHWGameplayAbility_TraceSteps DataHolder portant un TArray<FTraceStep>. Consommé par la task UHWAT_WaitMultiTraceForTargets pour déclencher des traces successives synchronisées avec les AnimNotify. Trace · Steps
UHWGameplayAbility_FakeProjectile Template de projectile (délai configurable avant spawn). Logique de spawn déléguée au Blueprint enfant. Utilisé par GA_MobFireball et autres abilities à projectile élémentaire. Projectile · Délai
UHWGameplayAbility_ApplyEventDamage Activée par événement (chute, piège). Extrait la magnitude via SetByCaller puis applique DamageEffect. Pas d'input direct. Trigger · Event

Étape 2 — Créer les GameplayEffects

2 / 8 · Cost · Cooldown · Damage · Tags
Effets de gameplay associés

Chaque ability nécessite un ou plusieurs GameplayEffects pour gérer ses coûts, son temps de recharge et ses effets sur la cible. Ces effets sont des assets Blueprint référencés par l'ability (ou appliqués dynamiquement via tasks).

Les coûts canoniques sont en Stamina pour les abilities physiques et Mana pour les compétences de Voie. Les valeurs varient avec le tier de skill et bénéficient d'un plancher réduit à palier 5 (Maître). Aucun cooldown GAS dédié pour les abilities de locomotion (gestion par états mutuellement exclusifs).

Cost Effect (Stamina) Déduit l'attribut Stamina du UHWCombatAttributeSet. Appliqué lors du CommitAbility. Exemple : attaque légère ~8 pts (plancher 4 pts à Maître), attaque lourde ~25 pts (plancher 12 pts), Signature ~150 pts (plancher 90 pts).
Cost Effect (Mana) Pour les compétences de Voie du Lien : déduit l'attribut Mana. Pool dérivé de Conscience + Esprit×2. Pas de barre Mana visible si aucune Voie n'est active.
Cooldown Effect Effet de type HasDuration. Octroie un tag de cooldown propre à l'ability (ex. Combat.Cooldown.Skill.WhirlSlash). Tant que l'effet est actif, l'ability ne peut pas être réactivée. Durée selon tier : Basique 5 s, Avancé 12 s, Expert 25 s, Signature 90 s.
Damage Effect (HWDamageGameplayEffect) Modifie l'attribut Health de la cible. Passe par le pipeline UHWGameplayEffectExecutionCalc qui intègre les multiplicateurs de Maîtrise d'arme, les critiques et les réactions élémentaires. Bloqué si la cible possède Combat.State.IFrame.
Ability_ActivateFail_* Tags d'échec d'activation propagés à l'UI : _IsDead, _Cooldown, _Cost, _TagsBlocked, _TagsMissing. Permettent au widget de skill bar d'afficher un feedback précis (gris, timer, icône ressource).
Compression Souffle (rappel) Le calcul final de dégâts applique la compression cosmique Si RawStat > 50 : RawStat = 50 + (RawStat − 50) × 0.7 aux 8 stats brutes capturées. Implémenté côté UHWGameplayEffectExecutionCalc — voir Code : Combat.

Étape 3 — Assembler un AbilitySet DataAsset

3 / 8 · UPrimaryDataAsset · Abilities · Effects · Attributes
UHWGameplayAbilitySet

Le UHWGameplayAbilitySet (dérivé de UPrimaryDataAsset) regroupe en un seul asset tout ce qu'un personnage doit recevoir : abilities, effets passifs et ensembles d'attributs. C'est l'unité d'octroi atomique du système.

Les handles générés lors de l'octroi sont stockés dans une FHWAbilitySet_GrantedHandles, ce qui permet le retrait propre via TakeFromAbilitySystem() en une seule opération (changement d'arme, deséquipement, mort, etc.).

GrantedGameplayAbilities TArray<FHWAbilitySet_GameplayAbility> : classe de l'ability (TSubclassOf<UHWGameplayAbility>), AbilityLevel et InputTag (FGameplayTag) qui liera cette ability à l'input du joueur.
GrantedGameplayEffects TArray<FHWAbilitySet_GameplayEffect> : classe du GE et EffectLevel. Utilisé pour les effets passifs permanents (régénération hors combat, buffs de base, tag Combat.Set.Unarmed, etc.).
GrantedAttributes TArray<FHWAbilitySet_AttributeSet> : classes d'UAttributeSet à octroyer. Garantit que le personnage possède les attributs nécessaires (ex. UHWCombatAttributeSet pour les abilities de combat).
FHWAbilitySet_GrantedHandles Structure de suivi : stocke tous les FGameplayAbilitySpecHandle, FActiveGameplayEffectHandle et références d'UAttributeSet octroyés. Méthode TakeFromAbilitySystem() retire tout en une passe.
Player_AbilitySet (asset principal) Asset BP de référence à /Game/AbilitySystem/AbilitySet/Player_AbilitySet. Octroie les ~38 abilities de base du joueur (locomotion + combat unarmed + dodges + caméra). Les abilities spécifiques aux armes équipées sont octroyées via des sets séparés au déséquipement/équipement.

Étape 4 — Octroi au personnage

4 / 8 · GiveToAbilitySystem · PossessedBy · DynamicAbilityTags
GiveToAbilitySystem

L'octroi des abilities au personnage se fait lors de la prise de possession par le contrôleur. Le UHWAbilitySystemComponent est initialisé via InitAbilityActorInfo, puis chaque AbilitySet est parcouru pour octroyer ses abilities, effets et attributs.

Le point clé : chaque FGameplayAbilitySpec créée stocke l'InputTag dans ses DynamicAbilityTags. C'est ce tag qui permettra au système d'input de retrouver l'ability correspondante par lookup tag à l'étape 5.

AHWGASCharacter::PossessedBy() Point d'entrée sur la classe de base. Appelle InitAbilityActorInfo(this, this) pour lier l'ASC à l'acteur (Owner) et à son avatar (Avatar).
AHWGASPlayerCharacter::PossessedBy() Surcharge joueur. Itère sur le tableau AbilitySets du personnage et appelle GiveToAbilitySystem() pour chaque set, en stockant les handles retournés dans GrantedHandles.
UHWGameplayAbilitySet::GiveToAbilitySystem() Crée un FGameplayAbilitySpec pour chaque ability du set, stocke l'InputTag dans Spec.GetDynamicSpecSourceTags(), et donne la spec à l'ASC via GiveAbility. Octroie également les GameplayEffects et instancie les AttributeSets.
Validation côté serveur L'octroi est authority-only : GiveAbility() n'est appelé que sur le serveur. Les specs sont ensuite répliquées aux clients via le mécanisme natif de l'ASC. Pour les Mobs, l'octroi se fait dans AHWGASMobCharacter::BeginPlay() côté serveur uniquement.
Persistance (rappel) Les abilities équipées sur la skill bar sont sérialisées et sauvegardées via OWS — voir étape 7 et le pipeline d'item pour la chaîne SaveAllProgression().

Étape 5 — Liaison des inputs

5 / 8 · UHWInputConfig · EnhancedInput · InputTag
UHWInputConfig et liaison par tags

Le UHWInputConfig (DataAsset) définit deux tableaux : NativeInputActions pour les actions système (mouvement caméra, look) et AbilityInputActions pour les actions liées aux abilities. Chaque entrée associe un UInputAction (EnhancedInput) à un FGameplayTag (InputTag).

Lors du setup des inputs, le UHWInputComponent mappe chaque InputAction d'ability vers les callbacks AbilityInputTagPressed et AbilityInputTagReleased, qui transmettent l'InputTag à l'ASC pour activation. Depuis la MAJ 2026-04-07, tous les inputs combat (weapon left/right, dash, sprint, crouch) sont gérés entièrement en C++ dans HWGASPlayerCharacter — les event graphs BP de BP_PlayerCharacter_CE ont été supprimés.

UHWInputConfig DataAsset contenant les mappings input. NativeInputActions : actions système sans lien GAS (ex. InputTag.Move, InputTag.Look.Mouse). AbilityInputActions : actions liées à des abilities via InputTag (ex. InputTag.Weapon.Left, InputTag.Dash, InputTag.Sprint).
SetupPlayerInputComponent() Appelé par AHWGASPlayerCharacter. Lie les inputs via UHWInputComponent en appelant BindAbilityActions() et en récupérant le mapping context EnhancedInput approprié.
BindAbilityActions() Parcourt les AbilityInputActions et mappe chaque input vers les callbacks AbilityInputTagPressed (appui) et AbilityInputTagReleased (relâchement) du UHWAbilitySystemComponent.
AbilityInputTagPressed(InputTag) Recherche les FGameplayAbilitySpec dont les DynamicAbilityTags contiennent l'InputTag reçu, et les ajoute à InputPressedSpecHandles pour traitement à la prochaine frame par ProcessAbilityInput().
Catalogue InputTag (extrait) InputTag.Weapon.Left (attaque arme principale), InputTag.Dash (esquive directionnelle), InputTag.Sprint, InputTag.Crouch, InputTag.Jump, InputTag.Aiming, InputTag.Flying, InputTag.ChangeCamera.

Étape 6 — Activation

6 / 8 · ProcessAbilityInput · CommitAbility · Ability Tasks
Pipeline d'activation

L'activation est orchestrée par ProcessAbilityInput(), appelé chaque frame par l'ASC. Cette méthode vérifie d'abord le tag TAG_Gameplay_AbilityInputBlocked, puis filtre les abilities selon leur ActivationPolicy et tente l'activation via TryActivateAbility().

Une fois activée, l'ability passe par CommitAbility qui valide les tags (en consultant le UHWAbilityTagRelationshipMapping), applique le coût (Stamina/Mana) et le cooldown, puis exécute la logique spécifique via des Ability Tasks asynchrones.

ProcessAbilityInput() Boucle frame par frame. Vérifie TAG_Gameplay_AbilityInputBlocked avant toute activation. Filtre par policy : OnInputTriggered sur InputPressedSpecHandles, WhileInputActive sur InputHeldSpecHandles. Vide les arrays après traitement.
TryActivateAbility() / Batched Tentative d'activation standard. Pour les abilities à cycle court (projectile spawn + EndAbility même frame), TryActivateAbilityBatchedAndEndInSameFrame() regroupe activation et fin dans un seul RPC serveur. ShouldDoServerAbilityRPCBatch() retourne true dans l'ASC custom.
DoesAbilitySatisfyTagRequirements() Vérifie les tags built-in (Required/Blocked sur l'ability) plus les exigences additionnelles définies dans UHWAbilityTagRelationshipMapping via GetAdditionalActivationTagRequirements(). Cette double couche permet de centraliser les règles inter-abilities sans modifier chaque BP.
ActivateAbility → CommitAbility CommitAbility applique le Cost Effect (déduit Stamina/Mana) et le Cooldown Effect (lance le tag de recharge). Si l'un échoue, l'ability ne s'exécute pas et le tag Ability_ActivateFail_Cost ou _Cooldown est propagé à l'UI.
Ability Tasks (asynchrones) Après le commit, l'ability exécute sa logique via tasks : PlayMontageAndWait (animation), WaitDelay, ApplyRootMotionConstantForce (dash, dodge), WaitInputRelease (toggle hold), WaitGameplayEvent.
Tasks custom HW UHWAT_WaitMultiTraceForTargets : traces multiples timées via FTraceStep (StartTimeInSeconds, AssociatedGE, Radius). UHWAbilityTask_WaitLanded : bind LandedDelegate du CMC (utilisé par GA_ApplyFallingDamage). AHWATA_ConeTrace : target actor cône (overlap sphère + filtre angulaire).
Réseau (LocalPredicted vs ServerOnly) Les abilities joueur sont LocalPredicted (réactivité immédiate, validation serveur). Les abilities Mob sont activées côté serveur uniquement via le BehaviorTree et BTTask_Abilities — pas de prédiction client. Voir Pipeline : Mob.

Étape 7 — Barre de compétences (UI)

7 / 8 · 10 slots · Cooldowns · Persistance OWS
UHWSkillBarComponent

Le composant UHWSkillBarComponent gère 10 slots de compétences. Chaque slot est une structure FHWSkillSlot contenant la référence à l'ability assignée, son tag, son icône, les informations de cooldown, l'état d'activabilité, le coût en ressource et le texte de la touche associée.

Le widget UHWSkillBarWidget s'abonne aux delegates du composant et met à jour l'affichage en temps réel via des événements Blueprint. La configuration des slots est sérialisée et sauvegardée via OWS (clé "SkillBar" dans AddOrUpdateCustomCharacterData) — voir Pipeline : Item pour la chaîne de persistance complète.

FHWSkillSlot Structure d'un slot : AssignedAbility (TSubclassOf<UHWGameplayAbility>), AbilityTag, Icon, CooldownDuration, CooldownRemaining, bCanActivate, ResourceCost, KeybindText.
AssignAbilityToSlot() Assigne une ability à un slot donné. Met à jour l'icône, le coût et le keybind. Diffuse le delegate OnSlotChanged. Vérifie que le tier de skill respecte la Maîtrise courante du joueur.
ActivateSlot() Active l'ability du slot via ASC->TryActivateAbilityByClass(). Vérifie d'abord que le slot contient une ability et que bCanActivate est true.
TickComponent → UpdateCooldowns() À chaque tick, interroge les effets de cooldown actifs sur l'ASC pour mettre à jour CooldownRemaining de chaque slot. Met à jour bCanActivate en fonction des Stamina/Mana courantes.
OnSlotChanged / OnCooldownStarted Delegates multicast. UHWSkillBarWidget s'y abonne pour mettre à jour l'UI : changement d'icône, lancement de l'animation de cooldown radial, grayout quand bCanActivate est false.
Persistance OWS La configuration des slots est sérialisée en JSON (assignation ability → slot) et envoyée via AddOrUpdateCustomCharacterData("SkillBar", JSON) dans la chaîne globale SaveAllProgression().

Étape 8 — Relations de tags

8 / 8 · UHWAbilityTagRelationshipMapping · Hiérarchie Combat.*
UHWAbilityTagRelationshipMapping

Le UHWAbilityTagRelationshipMapping (DataAsset à /Game/AbilitySystem/Tags/AbilityTagRelationshipMapping) contient un TArray<FHWAbilityTagRelationship> définissant les règles de blocage, d'annulation et de prérequis entre abilities sans coder ces règles dans chaque Blueprint.

Ce mapping est appliqué lors de l'initialisation du système via AHWGASPlayerCharacter::AbilitySystemInitialized() qui appelle UHWAbilitySystemComponent::SetTagRelationshipMapping(). Les règles sont ensuite consultées automatiquement dans DoesAbilitySatisfyTagRequirements() via GetAdditionalActivationTagRequirements().

FHWAbilityTagRelationship Structure d'une règle : AbilityTag (cible — peut être un parent), AbilityTagsToBlock, AbilityTagsToCancel, ActivationRequiredTags, ActivationBlockedTags.
GetAbilityTagsToBlockAndCancel() Itère le mapping ; pour chaque entrée dont AbilityTag est dans les tags de l'ability activée, append AbilityTagsToBlock et AbilityTagsToCancel aux containers de sortie.
GetRequiredAndBlockedActivationTags() Même parcours ; remplit ActivationRequiredTags et ActivationBlockedTags additionnels. Appelé depuis UHWAbilitySystemComponent::GetAdditionalActivationTagRequirements().
IsAbilityCancelledByTag() Retourne true si une entrée (AbilityTag == ActionTag) possède AbilityTagsToCancel.HasAny(AbilityTags). Permet une annulation contextuelle.
Performance Lookup en O(n) via boucle linéaire. Acceptable pour ≤50 entrées. Au-delà, un cache hashé serait à envisager.
— Hiérarchie de tags Combat.* (extrait canonique) —

Combat.State.* : ReadyToFight (posture combat active), Dead, Frozen, Blocking, DodgedRecently, Iframe (invulnérabilité dodge).

Combat.Set.* : Unarmed, SwordAndShield, Bow, etc. (un tag par catégorie d'arme équipée parmi les 13 types canoniques du combat).

Combat.Combo.Window.* : Window.1 (fenêtre 0.8 s entre deux coups d'un combo) — accordée par GE_ComboWindow01, requise par GA_Combo2. Voir Pipeline : Combo.

Combat.DamageType.* : Physical, Fire, Ice, Lightning, etc. — typent les dégâts sortants pour le calcul de réactions élémentaires.

InputTag.* : routage input → ability via DynamicAbilityTags. Ability_ActivateFail_* : feedback UI sur échec d'activation.

1. Spec Spec GDD : tier de skill (Basique → Signature), palier de Maîtrise requis (2 → 5), coût Stamina/Mana, cooldown, conditions cachées éventuelles.
2. Création Blueprint GA_* dérivé de UHWGameplayAbility (ou sous-classe : Dodge, MovementMode, ToggleState) + GameplayEffects associés.
3. Assemblage Regroupement dans un UHWGameplayAbilitySet avec GE et AttributeSets requis.
4. Octroi PossessedBy() octroie le set au personnage côté serveur, stocke les InputTags dans les DynamicAbilityTags.
5. Liaison UHWInputConfig lie les touches EnhancedInput aux InputTags, les callbacks transmettent à l'ASC.
6. Activation ProcessAbilityInput() → TryActivateAbility() → CommitAbility() → Ability Tasks asynchrones.
7. UI UHWSkillBarComponent met à jour cooldowns et état en temps réel via delegates ; configuration sauvegardée via OWS.
8. Relations UHWAbilityTagRelationshipMapping applique les règles de blocage/annulation/prérequis à chaque tentative d'activation.
