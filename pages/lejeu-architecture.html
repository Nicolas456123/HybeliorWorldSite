Architecture technique du projet HybeliorWorld

HybeliorWorld est un projet Unreal Engine 5.4 construit autour du Gameplay Ability System (GAS) pour la gestion des compétences, effets et attributs de combat. L'architecture MMO repose sur Open World Server (OWS), un backend .NET 6 en microservices conteneurisés qui gère l'authentification, la persistance des personnages, les instances de zones et la communication inter-serveurs.

Le code client compte environ 361 fichiers C++ (Public + Private) et ~50 fichiers C# côté backend. La banque d'assets totalise 32 307 assets dans /Game/ (textures, sons, animations, meshes, Blueprints, DataAssets, GameplayEffects, Widgets, Maps). L'ensemble est organisé en 2 modules projet (HybeliorWorld Runtime + HybeliorWorldEditor) et documenté en 11 sous-systèmes thématiques.

Moteur Unreal Engine 5.4 — Nanite, Lumen GI + Reflections, VSM, World Partition, Enhanced Input, CommonUI, DirectX 12 / Shader Model 6.
Gameplay Framework Gameplay Ability System (GAS) — Abilities, GameplayEffects, GameplayCues, AttributeSets, 122+ GameplayTags natifs déclarés en C++.
Backend MMO Open World Server (OWS) — 6 microservices .NET 6 (PublicAPI :44302, CharacterPersistence :44323, InstanceMgmt :44328, GlobalData :44325, InstanceLauncher, GlobalDataReplication), 33 tables SQL (MSSQL / PostgreSQL / MySQL au choix).
Infrastructure Docker + Docker Compose · Nginx 1.25 (SSL) · Redis 7 Alpine (512 MB LRU, sessions) · RabbitMQ 3.x (queues SpinUp/ShutDown) · ELK Stack 8.11 (logs).
Code C++ ~361 fichiers source répartis entre Public/ (headers) et Private/ (implémentation). Migration BP→C++ massive (1500+ nœuds Blueprint convertis).
Assets Blueprint 32 307 assets dans /Game/ — top catégories : Texture2D (6 407), SoundWave (4 017), SoundCue (3 756), AnimSequence (3 457), StaticMesh (2 612), SkeletalMesh (1 997), Blueprint (215), DataTable (109).

Migration Accord — Stratégie 2026

Pivot canonique · 6 phases A → F
Pourquoi : refonte sémantique XP/Level → Souffle / Accord / Ères

Avant la refonte 2026-04/05, HybeliorWorld utilisait un modèle classique : CharacterLevel (1 → ~100), XP cumulés, 10 attributs D&D (Strength, Agility, Constitution…), récompenses de quêtes ExperienceReward + GoldReward, courbe de maîtrise XP × 1.15^N.

La refonte canonique 2026 abandonne le concept de niveau global au profit d'un système à 5 couches : 4 stats fondamentales (Vitalité, Souffle, Présence, Conscience), 8 stats brutes (Vigueur, Vivacité, Endurance, Acuité, Esprit, Résonance, Mémoire, Verbe — compressées au-dessus de 50), Maîtrises 5 paliers (Novice → Maître, avec rouille post-Souffle), L'Accord (0-100 % d'alignement avec l'Ère active), L'Héritage (Ères Concordées, titres permanents). Cette refonte résout d'un coup : power creep, barrière à l'entrée, stagnation, wipe brutal et lore détaché.

Comment : migration parallèle sans breaking change OWS

Principe : OWS bootstrap, FUserCharacter, tables SQL Characters et CharHasAbilities continuent de fonctionner identiquement côté technique. Aucun breaking change réseau. CharacterLevel et XP deviennent des champs techniques internes (matchmaking, scaling, statistiques serveur) — jamais exposés au joueur dans le HUD ou les UI de progression.

Phase A — Schéma SQL Ajout de 4 colonnes côté table Characters ou table liée : CurrentEraAccord (FLOAT 0-100), ConcordedErasCount (INT), EraAccordsHistory (JSON), CurrentMasteryRustLevel (FLOAT). Aucun DROP des colonnes existantes. Migration ALTER TABLE non bloquante (< 1 min sur sandbox). SQL · Additif
Phase B — Lecture/écriture client UHWProgressionComponent lit/écrit CurrentEraAccord à chaque event gameplay pertinent. L'UI bascule sur l'Accord. CharacterLevel / XP deviennent invisibles côté HUD. Tests unitaires vérifient qu'aucune UI ne lit plus CharacterLevel. Client · UI
Phase C — Mapping 8 stats brutes Nouvelles colonnes RawStat_Vigueur, RawStat_Vivacite, etc. (FLOAT 0-150). Projection des 10 attributs D&D existants : Strength → Vigueur, Agility → Vivacité, Constitution → Endurance, Wisdom → Conscience, Intellect → Esprit… Stats UE manquantes (Acuité, Résonance, Mémoire, Verbe) ajoutées comme nouvelles colonnes. Stats · Couche 1
Phase D — Compression Souffle UHWGameplayEffectExecutionCalc applique la règle « stats > 50 ramenées 30 % vers 50 » côté combat, sans modifier la valeur stockée. Empêche le power creep linéaire au-delà du seuil 50. Combat · Compression
Phase E — Maîtrises 5 paliers La courbe XP × 1.15^N est remplacée par 5 seuils discrets (Novice → Apprenti → Adepte → Expert → Maître). Les MasteryLevel int32 actuels sont mappés via une table de transposition (0 = Novice, 1-5 = Apprenti, 6-15 = Adepte, 16-30 = Expert, > 30 = Maître). Rouille post-Souffle (-15 % à dissiper par usage). Maîtrise · Rouille
Phase F — Migration soft (optionnel) Conversion des anciens CharacterLevel en ConcordedErasCount selon une table de pondération (ex. niveau 50 = 3 ères concordées). Validation requise. Phase optionnelle, non bloquante. Soft · Optionnel
— Pourquoi pas de breaking change OWS —

FUserCharacter (OWS2API.h) garde tous ses champs. Le client lit ces champs et les ignore visuellement, mais le serveur les écrit toujours. Les microservices PublicAPI / CharacterPersistenceAPI sont inchangés. OWSPlayerControllerComponent::UpdateCharacterStats() continue de fonctionner.

Stratégie V3 = documentation seule. Les phases A à F seront planifiées et déclenchées post-V4. Chaque fichier de documentation impacté ([[SQL Characters]], [[Combat Attribute Set]], [[Quest System]], [[HW Progression Component]], [[Weapon Mastery]]…) porte un avertissement renvoyant à la stratégie centrale.

Plugins et Dépendances

19 plugins actifs · 2 modules projet
Écosystème de plugins (vérifié contre HybeliorWorld_5.4.uproject)

Le projet déclare 19 plugins actifs (Epic officiels + tiers) et 2 modules projet (HybeliorWorld Runtime / PostConfigInit + HybeliorWorldEditor Editor / PostEngineInit). Note : le système Water (ex-Oceanology) est intégralement fusionné dans le module HybeliorWorld en C++ natif — Oceanology_Plugin n'est pas activé (assets legacy à purger).

OWSPlugin (5.4) Framework MMO backend (Open World Server) — LoadingPhase PreDefault, dépend de GameplayAbilities + ReplicationGraph. Classes : OWSGameInstance, OWSGameMode, OWSPlayerState, OWSPlayerControllerComponent, OWSAPISubsystem.
GameplayAbilities (5.4) Plugin Epic officiel — Gameplay Ability System complet : Abilities, Effects, Cues, AttributeSets, Tags, Tasks. Cœur du système de combat et de compétences.
ReplicationGraph (5.4) Optimisation de la réplication réseau pour les environnements massivement multijoueurs. Gestion spatiale des acteurs répliqués selon distance et pertinence.
CommonUI (5.4) Framework UI d'Epic pour la gestion multi-plateforme des interfaces. Navigation par stack, support gamepad natif, gestion des focus et des couches d'UI.
TargetingSystem (5.4) Système de ciblage avancé — sélection de cibles par filtres (distance, angle, type, faction), utilisé par le GAS pour les abilities et les GameplayEffects.
Niagara (5.4) Système d'effets visuels particules — VFX gameplay, météo, projectiles magiques, GameplayCues visuels.
PCG + PCGBiomeCore + PCGBiomeSample + PCGGeometryScriptInterop (5.4) Procedural Content Generation — placement de végétation, rochers, détails de terrain. 4 graphes actifs (Temperate Forest, Hot Desert, MultiBiome, Basic).
GeometryScripting + ProceduralMeshComponent (5.4) Génération géométrique procédurale — utilisée par le terrain SDF caves, l'érosion hydraulique et le Marching Cubes.
LiveLink (5.4) Pipeline d'animation temps réel — connexion avec des outils externes (Maya, MotionBuilder, capture faciale) pour le streaming d'animation en direct dans l'éditeur.
GASAttachEditor (1.9) Outil de debug GAS — inspection des attributs, tags actifs et effets en cours sur n'importe quel ASC en jeu.
LowEntryExtStdLib (5.3) Bibliothèque d'utilitaires Blueprint étendant les fonctionnalités standards d'UE5.
ModelingToolsEditorMode + BlockoutToolsPlugin (5.4) Outils éditeur de modélisation et de blockout level design.
VisualStudioTools (5.4) Intégration Visual Studio 2022 (Win64) — symboles de debug, navigation source.
UnrealMCP (1.0) Bridge Claude Code HTTP — port :3001, plugin éditeur Win64 PostEngineInit. Routes : /status, /log, /livecoding, /bp/* (manipulation Blueprints nodaux). Pipeline d'outillage IA pour l'édition assistée.

Hiérarchie des Personnages

Héritage C++ · 5 classes
Chaîne d'héritage des classes Character

L'architecture des personnages suit une hiérarchie d'héritage stricte, partant de la classe de base Unreal ACharacter jusqu'aux spécialisations joueur et entités (mobs / PNJ). Chaque niveau ajoute une couche de fonctionnalité sans dupliquer de logique. La nomenclature canonique 2026 utilise AHWGASEntityCharacter pour la branche non-joueur (transition documentaire en cours côté code, où l'on trouve aussi historiquement AHWGASMobCharacter).

ACharacter Classe de base Unreal Engine — CharacterMovementComponent, CapsuleComponent, SkeletalMesh. Gère le déplacement physique, la gravité, le networking de base. UE5 · Base
AHWCharacter Classe de base HybeliorWorld — système d'apparence personnalisable (10 anatomies : Human F/M Adult+Child, Dwarf F/M, Elf F/M, Orc F/M), composant de ciblage (lock-on), animations de base, interface d'interaction. Tous les personnages du jeu héritent de cette classe. Apparence · Ciblage
AHWGASCharacter Intégration complète du GAS — AbilitySystemComponent, UHWCombatAttributeSet (15 attributs répliqués, mappés vers les 8 stats brutes canoniques), application et réception de GameplayEffects, GameplayTags d'état. Classe parente commune aux joueurs et aux entités. GAS · Attributs · Combat
AHWGASPlayerCharacter Spécialisation joueur — gestion des inputs (Enhanced Input · 28 Input Actions), caméra troisième personne, système d'équipement (16 slots), UHWSkillBarComponent (10 slots), inventaire double (sac + équipement), intégration UI/HUD, persistance via OWS. Joueur · Input · Équipement
AHWGASEntityCharacter Spécialisation entités (mobs / PNJ) — contrôleur IA (Behavior Tree + Blackboard, AHWAIController avec AIPerception SightRadius 3000), pool d'entités pré-instanciées (50 mobs), UHWLootTable, nameplate dynamique. 10 variants cosmiques canoniques selon l'Ère active. IA · Loot · Spawner · Variants cosmiques

ACharacter → AHWCharacter (apparence, ciblage) → AHWGASCharacter (GAS, 15 attributs) →
    ├── AHWGASPlayerCharacter (input, caméra, équipement, UI)
    └── AHWGASEntityCharacter (IA, loot, pool, variants cosmiques)

Flux d'initialisation et de persistance

Cascade pondérée · auto-save 5 min · OWS
Initialisation : étapes nommées et pondérées (AHWPlayerController)

Le système d'initialisation utilise des étapes FHWInitializationPart avec poids cumulatif, chacune appelant PartialInitializationComplete(StepName). Côté serveur : "GAS" 25 % + "CUSTOMCHARACTERDATA" 50 % + "PLAYERSTATE" 25 %. Côté client : "PLAYERSTATE" 50 % + "SERVERSIDEDONE" 50 %. Quand toutes les étapes d'un côté sont complétées, ReadyToPlay() est déclenché.

Persistance : clés Custom Character Data + auto-save

Toutes les données de personnage sont persistées via l'API OWS sous forme de clés JSON nommées : "OftenChangeCharacterData", "ChangeCharacterData", "RarelyChangeCharacterData", "CharacterAppearance", "CharacterAppearanceCE", "BaseCharacterSkills", "WeaponMastery", "CharacterProgression", "SkillBar", "QuestProgress", "SupplyPodsOpened", "ContainersOpened", "*Inventory*".

Timers : PersistenceDataTimer 10 s (loop) — RunPersistenceData() serveur · AutoSaveProgressionTimer 300 s (5 min loop) — SaveAllProgression() (mastery + progression + skill bar + quêtes). Flush au logout dans un ordre critique (BagInventory → EquipmentInventory → 3 CharacterData) pour éviter la race condition.

Configuration

.ini · GameplayTags · Enhanced Input · Secrets
Fichiers de configuration clés

La configuration du projet est répartie entre les fichiers .ini d'Unreal et les systèmes de tags / input intégrés au GAS. Configuration multi-environnement (dev / staging / prod / secrets) avec .gitignore sécurisé pour les credentials.

DefaultGame.ini Configuration OWS — URL de l'API backend, CustomerGUID, paramètres de session, timeouts réseau. Paramètres GAS globaux : modes de prédiction, réplication des GameplayEffects, politique de tags. PrimaryAssetTypesToScan à compléter (QuestData, HWUnlockDefinition non encore enregistrés — dette connue).
DefaultGameplayTags.ini + déclarations C++ 122+ GameplayTags natifs déclarés en C++ (aucun tag exclusivement en .ini). Hiérarchie : CombatTags (états, types de dégâts, conditions, flags critique), InputTags (binding GAS), AbilityTags (activation, cooldown, blocage), EquipmentTags (slots, armes, rareté).
Enhanced Input 28 Input Actions · 2 Input Mapping Contexts (clavier/souris + manette) · UHWInputConfig (DataAsset mappant InputActions ↔ Gameplay Tags) · support du remapping en jeu via UHWSettingsLocal.
DefaultGame_Secrets.ini Variables sensibles (API keys, tokens) exclues du contrôle de version. Ajout de EncryptionKey, credentials RabbitMQ et secrets OWS séparés des configs publiques.
— Stack technique résumé —

Client : Unreal Engine 5.4 · C++ (HybeliorWorld module) · Blueprints · GAS · Enhanced Input · CommonUI · World Partition · Nanite · Lumen · PCG · Niagara · DirectX 12 / SM 6

Réseau : OWSPlugin (PreDefault) · ReplicationGraph (MMO spatial) · Dedicated Servers · Zone-based instancing · Server travel · HardCap 80 joueurs / instance

Backend : Open World Server (.NET 6) · 6 microservices REST · MSSQL / PostgreSQL / MySQL · Redis 7 · RabbitMQ 3 · Nginx 1.25 SSL · ELK 8.11 · Docker Compose · Migration Accord en cours (V3 doc, post-V4 SQL)
