Open World Server · 6 microservices .NET 6 · 33 tables SQL
Backend MMO d'HybeliorWorld

L'architecture serveur d'HybeliorWorld repose sur Open World Server (OWS), un framework backend MMO open-source édité par Sabre Dart Studios. OWS fournit un ensemble de 6 microservices ASP.NET Core 6 conteneurisés, une base de données relationnelle multi-moteur (MSSQL · PostgreSQL · MySQL) et un plugin UE5 (OWSPlugin) servant de pont HTTP entre le client et l'API.

Le projet utilise OWS comme socle de persistance des personnages, gestion des sessions, orchestration des instances de zone et stockage des données globales. Toutes les écritures côté client passent par UOWSPlayerControllerComponent (HTTP avec retry et backoff). Le couplage avec la refonte canonique 2026 (Souffle / Accord / Ères) est piloté par le document Migration Accord — stratégie parallèle, pas de breaking change OWS.

Pile technique ASP.NET Core 6.0 · Dapper (SQL léger) · SimpleInjector (IoC) · Serilog (logs ELK) · Swagger / Swashbuckle · IMemoryCache (cache 5 min in-process). Tous les services exposent /swagger.
Multi-tenant Chaque client OWS est identifié par un CustomerGUID unique. Toutes les requêtes API portent un header X-CustomerGUID validé par StoreCustomerGUIDMiddleware. Les tables SQL sont partitionnées par cette GUID — un tenant ne voit jamais les données d'un autre.
Multi-moteur SQL Switch via la variable OWSStorageConfig:OWSDBBackend (mssql · postgres · mysql). Implémentations Dapper dans OWSData.Repositories.Implementations.{MSSQL,Postgres,MySQL}. Cache 5 min présent uniquement côté MSSQL ; absent côté Postgres/MySQL.
Plugin UE5 OWSPlugin 5.4 (Sabre Dart Studios) — LoadingPhase PreDefault. Classes principales : UOWSGameInstance, UOWSPlayerControllerComponent, UOWSAPISubsystem, AOWSGameMode, AOWSPlayerState. Dépend de GameplayAbilities + ReplicationGraph.
Infrastructure Docker Compose · Nginx 1.25 (reverse proxy SSL) · RabbitMQ 3.13 (queues SpinUp/ShutDown) · Redis 7 Alpine (cache distribué cible) · ELK 8.x (Elasticsearch + Logstash + Kibana). Cible production : Kubernetes 1.28+ avec Kustomize.
Authentification Auth interne via stored procedure PlayerLoginAndCreateSession (table UserSessions → UserSessionGUID). Auth externe via IExternalLoginProvider (Epic Online Services implémenté ; Xsolla en stub).

Migration Accord — côté serveur

Stratégie parallèle · pas de breaking change OWS
Pourquoi : la refonte canonique 2026 ne casse rien côté backend

La refonte Souffle / Accord / Ères abandonne le concept de niveau global au profit du système 5-couches (4 fondamentales + 8 stats brutes + 5 paliers Maîtrise + Accord 0-100 % + Héritage permanent). Côté serveur, OWS continue d'écrire les colonnes historiques (CharacterLevel, XP, 10 attributs D&D) sans aucune modification. L'enjeu de la migration est donc sémantique et additif, pas destructif.

Cette section décrit comment la refonte se branche sur OWS. La stratégie complète — incluant les phases A à F et les colonnes SQL cibles — est centralisée dans la page Architecture. Cette page-ci documente uniquement le périmètre serveur.

Tables conservées intactes Characters (80+ colonnes dont CharacterLevel, XP, Strength, Agility, Constitution...) garde toutes ses colonnes. Class, CharHasAbilities.AbilityLevel, Items.ItemTier, WorldSettings : aucun DROP. Le code .NET (`PlayerLoginAndCreateSession`, `UpdateCharacterStats`, etc.) reste valide. Aucun DROP
Colonnes additives (Phase A) Ajout via ALTER TABLE non bloquant : CurrentEraAccord (FLOAT 0-100), ConcordedErasCount (INT), EraAccordsHistory (JSON ou table liée), CurrentMasteryRustLevel (FLOAT, rouille post-Souffle). Migration estimée < 1 min sur sandbox. SQL · Additif
Champs FUserCharacter inchangés La struct FUserCharacter dans OWS2API.h conserve l'intégralité de ses 100+ champs (Level, XP, 10 attributs D&D, ressources, combat, monnaies). Le client UE5 lit ces champs mais les ignore visuellement côté HUD. Pas de breaking change réseau, pas de version d'API à bumper. Plugin OWS
CustomCharacterData : véhicule de la refonte La table CustomCharacterData (paire CustomFieldName / FieldValue JSON) sert de couche d'extension non-intrusive. Les nouvelles données canoniques (Accord, Héritage, Maîtrises 5 paliers, rouille) y sont sérialisées sous des clés dédiées : "CharacterProgression", "WeaponMastery", "QuestProgress", etc. Pas de schéma SQL à toucher pour ces clés. Custom · JSON
GlobalData : XPMultiplier → EraAccordMultiplier La clé GlobalData XPMultiplier (multiplicateur d'XP serveur) est à renommer à terme en EraAccordMultiplier pour refléter la refonte (multiplicateur appliqué à l'AccordGain selon l'alignement avec l'Ère active). La clé reste lisible en V3 ; le renommage se fera au boot des Phases B-C. GlobalData · Sémantique
Code mort à terme Fonctions SQL AbilityMod (modificateur D&D) et RollDice deviennent du code mort post-Phase C — elles présupposent le modèle d'attributs D&D incompatible avec les 8 stats brutes canoniques. Décision : neutralisation (pas DROP) pour préserver l'historique. D&D · À neutraliser
— Pourquoi pas de breaking change —

OWS bootstrap est un framework partagé avec d'autres jeux. Forker la struct FUserCharacter ou supprimer des colonnes Characters casserait la rétrocompatibilité du plugin. La stratégie retenue est donc additive et sémantique : le code .NET reste identique, le code UE5 lit les nouveaux champs en parallèle, et la doc est à jour.

V3 = documentation seule. Les phases A à F (schéma SQL, lecture/écriture client, mapping 8 stats brutes, compression Souffle, Maîtrises 5 paliers, migration soft optionnelle) sont planifiées post-V4. Voir page Architecture pour le détail des 6 phases et les risques associés.

Microservices .NET 6

6 services REST · ports dev :44302-44328
Architecture microservices conteneurisée

Chaque microservice est une application ASP.NET Core 6.0 autonome, exposée derrière le reverse proxy Nginx. Communication inter-services via HTTP (sans TLS interne actuellement, dette sécurité). Health check : exécution d'un bash -c 'exec 3<>/dev/tcp/127.0.0.1/80' toutes les 30 s sur le port 80 interne. Tous les services portent leur propre OpenAPI / Swagger UI.

OWSPublicAPI Port dev :44302 · Authentification, comptes utilisateurs, sessions, personnages. Endpoints clés : LoginAndCreateSession, RegisterUser, ExternalLoginAndCreateSession (Epic / Xsolla), GetAllCharacters, CreateCharacter, UserSessionSetSelectedCharacter, GetServerToConnectTo, Logout. Aucun RemoveCharacter dans le contrôleur (suppression côté CharacterPersistence). Auth · Users
OWSCharacterPersistence Port dev :44323 · Persistance des stats, inventaire, custom data, abilities. Routes : /api/Characters/ (UpdateCharacterStats, UpdateAllPlayerPositions, AddOrUpdateCustomData, GetCustomData, GetByName, PlayerLogout) et /api/Abilities/ (CRUD GAS abilities + barres). Cible privilégiée des appels périodiques d'auto-save. Persistance · GAS
OWSInstanceManagement Port dev :44328 · Orchestration des serveurs et instances de zones. Routes /api/Instance/ et /api/Zones/ : RegisterLauncher, SpinUpServerInstance, ShutDownServerInstance, StartInstanceLauncher, SetZoneInstanceStatus, GetServerToConnectTo, GetZoneInstancesForZone, UpdateNumberOfPlayers, AddZone. Publie sur les queues RabbitMQ. Instances · Zones
OWSGlobalData Port dev :44325 · Stockage clé/valeur partagé à l'échelle du serveur. Endpoints minimaux : POST /api/GlobalData/AddOrUpdateGlobalDataItem, GET /api/GlobalData/GetGlobalDataItem/{key}. Cache 5 min via IMemoryCache côté MSSQL (absent en Postgres/MySQL — cohérence multi-instance limitée). Cas d'usage : WorldTime, ServerEvents, MaintenanceMode, EraAccordMultiplier. Clé/Valeur
OWSManagement Port dev :5205 · Console d'administration. Backend ASP.NET Core 6 (UsersController CRUD complet) + frontend SPA Vue.js 3 + Vuetify 3 + TypeScript + Vite. Sections du menu : Dashboard · Users · Characters · World Servers · Zones · Zone Instances · Global Data · Settings. Seul Users est entièrement câblé ; les autres grids sont des squelettes prêts à connecter. Admin · Vue 3

Écoute les queues RabbitMQ ows.serverspinup.{worldServerId} et ows.servershutdown.{worldServerId}. Lance et tue des processus UE (UnrealEditor.exe ou serveur dédié) via Process.Start. Plugin UE5 — OWSPlugin

UOWSGameInstance · UOWSPlayerControllerComponent · UOWSAPISubsystem
Pont HTTP entre UE5 et le backend OWS

Le plugin OWSPlugin 5.4 est chargé en LoadingPhase: PreDefault avec dépendances GameplayAbilities + ReplicationGraph. Il fournit les classes de base (Game Mode, Player State, Game Instance) et les composants client (controller, subsystems) qui exposent l'API OWS aux blueprints et au C++ HybeliorWorld.

Toutes les requêtes HTTP passent par le pattern retry + backoff avec MaxRetryCount = 3 par défaut, suivi de performance via RequestStartTimes : TMap<FString, double>, et logging automatique de la durée ([OWS] API Request <url> completed in <N> ms).

UOWSGameInstance Hérite de UGameInstance. Cycle de vie (BeginLoadingScreen, EndLoadingScreen), chargement d'assets depuis chemins (LoadWeaponActorClassFromPath, LoadStaticMeshFromPath, FindGameplayAbilityClass), chiffrement AES-128 (EncryptWithAES avec marqueur OWS#@!). Stocke UserSessionGUID (FString BP).
UOWSPlayerControllerComponent UActorComponent · BlueprintSpawnableComponent. Centralise les opérations API. Méthodes : TravelToMap2 (coordonnées chiffrées AES), GetCharacterStats, UpdateCharacterStats, GetCustomCharacterData, AddOrUpdateCustomCharacterData, GetCharacterAbilities, SavePlayerLocation, SaveAllPlayerData, PlayerLogout. Chaque méthode expose OnNotify...Delegate (succès) et OnError...Delegate (échec).
UOWSAPISubsystem UGameInstanceSubsystem singleton créé avec la GameInstance. Lit la config dans Initialize() (OWSAPICustomerKey, 4 URLs API, timeout 30 s). API GlobalData (GetGlobalDataItem, AddOrUpdateGlobalDataItem) et création de personnage par défaut (CreateCharacterUsingDefaultCharacterValues).
AOWSGameMode Mode de jeu serveur dédié. Propriétés : CharactersOnline, IAmZoneName, ZoneInstanceID, SaveIntervalInSeconds, DayLengthInSeconds, DaysPerLunarCycle, DaysPerSolarCycle. Méthodes : AddZone, UpdateNumberOfPlayers, SaveAllPlayerLocations, GetGlobalDataItem. Référencé par AHWGameMode (HybeliorWorld) qui l'étend.
AOWSPlayerState APlayerState + données OWS répliquées : PlayerStartLocation (FVector), PlayerStartRotation, DefaultPawnClass (FString), UserSessionGUID (FString), AlwaysRelevantPartyID (int32).
FPendingRetryRequest Struct interne : ApiModuleToCall, ApiToCall, PostParameters, RetryCount, NextRetryTime, pointeur vers callback. Retry automatique sur échec connexion ou HTTP 5xx (les 4xx ne sont pas retentés).
— Architecture HTTP — flux requête typique —

Struct UE → FJsonObjectConverter::UStructToJsonObjectString → ProcessOWS2POSTRequest (header X-CustomerGUID, Content-Type: application/json, User-Agent: X-UnrealEngine-Agent) → callback On[Action]ResponseReceived → ProcessAPIResponse (vérifie ErrorMessage absent) → GetJsonObjectFromResponse → GetStructFromJsonObject<T> → délégate OnNotify... ou retry puis OnError....

Login Providers — auth externe

IExternalLoginProvider · Epic Online Services · Xsolla (stub)
Abstraction unifiée pour fournisseurs OAuth tiers

Le module OWSExternalLoginProviders fournit un pattern Factory + Strategy pour intégrer des fournisseurs d'identité externes. Toutes les implémentations héritent de la classe abstraite générique ExternalLoginProvider<TOptions> et exposent les méthodes du contrat IExternalLoginProvider : AuthenticationRedirect, AuthenticatePasswordAsync, AuthenticateAuthorizationCodeAsync, AuthenticateAuthorizationExchangeAsync, AuthenticateDeviceToken, TwoFactorAuthentication, VerifyToken.

Fabrique : ExternalLoginProviderFactory (basée sur SimpleInjector, dictionnaire insensible à la casse). Réponses unifiées via le DTO ExternalLoginProviderResponse (IsError, ErrorDescription, TwoFactorAuthenticationRequired, AccessToken). L'auth externe contourne PlayerLoginAndCreateSession mais réutilise la table UserSessions.

Epic Online Services (EOS) Implémentation complète. Endpoint OAuth : POST https://api.epicgames.dev/epic/oauth/v1/token. Auth client : HTTP Basic (RFC 6749) avec ClientId:ClientSecret. Grant types supportés : authorization_code (standard), exchange_code (propriétaire Epic, via launcher), redirect OAuth (scope=basic_profile, state anti-CSRF). Non supportés : password, device token, 2FA. Verification JWT à deux niveaux (introspection online + JWKS offline avec cache 24 h). EOS · Complet
Xsolla Stub vide. La classe XsollaLoginProvider existe mais n'hérite pas de ExternalLoginProvider<TOptions> et ne contient aucune méthode. La constante ExternalLoginProviderOptions.Xsolla est déclarée pour une future implémentation. ExternalLoginProviderFactory.Get("Xsolla") ne peut pas résoudre une instance utilisable. Xsolla · Stub
Steam (futur) Pas de fournisseur Steam direct dans le code OWS actuel. Implémentation possible via SteamLoginProvider : ExternalLoginProvider<SteamOptions> avec ApiKey + AppId, validation du ticket session via l'API Steam Web (AuthenticateUserTicket/v1). Côté UE5 : utiliser le plugin OnlineSubsystemSteam pour récupérer le ticket. Nouvelle constante "Steam" à ajouter dans ExternalLoginProviderOptions. Steam · Hypothétique
— Cache JWKS et VerifyToken —

Pour la vérification offline des JWT Epic, les clés JWKS sont mises en cache via IMemoryCache avec une TTL 24 h (clé "epicgames.jwks"). La stratégie est dual : niveau 1 appel d'introspection online (tokenInfo), niveau 2 validation JWT locale si le niveau 1 échoue (vérifie les claims aud = ClientId et pfdid = DeploymentId). Limitation connue : jwks.Keys.First() n'itère pas sur toutes les clés en cas de rotation.

Bug potentiel signalé dans AuthenticateAuthorizationExchangeAsync : la ligne response.AccessToken = request.AccessToken; est manquante par rapport à AuthenticateAuthorizationCodeAsync.

Communication client ↔ serveur

Custom Character Data · clés OWS · auto-save 5 min
Persistance via clés JSON nommées sur CustomCharacterData

Toutes les données de personnage sont persistées via l'API OWS sous forme de clés JSON nommées dans la table CustomCharacterData. La clé fonctionne comme une extension non-intrusive : aucun ALTER TABLE pour ajouter une donnée, le serveur écrit/lit du FieldValue : TEXT.

Pattern : UOWSPlayerControllerComponent::AddOrUpdateCustomCharacterData(KeyName, JSONValue) côté UE5 → POST /api/Characters/AddOrUpdateCustomData côté OWS → stored procedure AddOrUpdateCustomCharData en SQL → upsert. Lecture symétrique via GetCustomCharacterData(KeyName).

"OftenChangeCharacterData" Données fréquemment modifiées (position, ressources courantes). Sauvegarde via PersistenceDataTimer 10 s.
"ChangeCharacterData" / "RarelyChangeCharacterData" Données moyennement / rarement modifiées (équipement, customisation). Sauvegarde sur événement ou auto-save 5 min.
"CharacterAppearance" / "CharacterAppearanceCE" Personnalisation visuelle (10 anatomies, morph targets, presets). CharacterAppearanceCE = struct binaire compacte.
"BaseCharacterStats" État initial des 10 attributs D&D (Strength, Agility, Constitution... — JSON). Cible Migration Accord : projection vers les 8 stats brutes canoniques (Vigueur, Vivacité, Endurance, Acuité, Esprit, Résonance, Mémoire, Verbe — Phase C).
"BaseCharacterSkills" Compétences GAS de base : {"Skill1": 1, ...}.
"WeaponMastery" Maîtrises d'armes par type (Sword, Axe, Mace, Dagger, Bow, Staff, Spear, Shield). Cible canonique : 5 paliers (Novice → Apprenti → Adepte → Expert → Maître) + rouille post-Souffle (-15 %, dissipée par usage). Implémentation post-V4.
"CharacterProgression" Progression cachée (UHWProgressionComponent) : table EHWConditionType/SubjectTag → progression en clé composite. Cible Migration Accord : c'est ici que vivront CurrentEraAccord, ConcordedErasCount et l'Héritage (titres, recettes, lore entries permanents).
"SkillBar" Configuration de la barre d'abilities du joueur (10 slots).
"QuestProgress" État complet des quêtes (statuts + progression objectifs) sérialisé en JSON par UHWQuestComponent::SerializeQuests. Format : {"statuses": {tag: int}, "progress": {key: float}}.
"SupplyPodsOpened" / "ContainersOpened" Listes des supply pods / containers ouverts par le joueur (anti-doublon de loot).
"BagInventory" / "*Inventory*" Inventaire sérialisé (FHWInventoryMaster) avec FastArraySerializer. Sauvegarde push-based sur événement de modification.
— Timers de persistance et flush au logout —

Côté AHWPlayerController : PersistenceDataTimer 10 s (loop) appelle RunPersistenceData() côté serveur · AutoSaveProgressionTimer 300 s (5 min loop) appelle SaveAllProgression() qui flush WeaponMastery + CharacterProgression + SkillBar + QuestProgress.

Flush au logout dans un ordre critique pour éviter la race condition : BagInventory → EquipmentInventory → 3 CharacterData (Often / Change / Rarely) → Progression / Quest. UOWSPlayerControllerComponent::PlayerLogout appelle ensuite la stored procedure PlayerLogOut côté SQL (supprime les entrées CharOnMapInstance).

Infrastructure et DevOps

Docker · RabbitMQ · ELK · Kubernetes
Stack opérationnelle complète, conteneurisée

Le déploiement local utilise Docker Compose avec 4 réseaux isolés (frontend, backend, database, elk — les 3 derniers en internal: true, accessibles uniquement via Nginx). Les volumes persistants sont nommés ows2-postgres-data, ows2-elasticsearch, ows2-messaging, ows2-redis-data. La cible production est Kubernetes 1.28+ orchestré par Kustomize.

Docker Compose — 13 services owspublicapi, owsinstancemanagement, owscharacterpersistence, owsglobaldata, owsmanagement · database (PostgreSQL 16, port 5432) · messaging (RabbitMQ 3.13, ports 5672/15672) · redis (7 Alpine, 6379) · nginx (1.25, 80/443 SSL) · elasticsearch (8.x, 9200/9300) · logstash (5044/9600) · kibana (5601) · heartbeat (disponibilité services).
RabbitMQ — queues SpinUp / ShutDown 2 exchanges direct non durables : ows.serverspinup et ows.servershutdown. Routing key par launcher : ows.serverspinup.{worldServerId}. Queue exclusive auto-delete par instance launcher. autoAck: true (pas de requeue), QoS prefetch: 1. Vérification CustomerGUID seule couche de sécurité sur les messages.
Redis Cache 7 Alpine, 512 MB LRU. Cible : sessions et cache distribué pour résoudre la limite de cohérence multi-instance du IMemoryCache local 5 min de OWSGlobalData. Voir Pistes d'extension Global Data Replication §"Cache distribué".
ELK Stack Elasticsearch 8.x + Logstash + Kibana. Sink Serilog HTTP http://localhost:50000 (format Elasticsearch JSON, bufferisé via DurableHttpUsingFileSizeRolledBuffers). Enrichers : FromLogContext, WithExceptionDetails, WithMachineName, WithCorrelationId. Niveau minimum : Debug. Surcharge Microsoft : Information.
Kubernetes — Kustomize Namespace ows isolant tous les pods. Deployments (5 microservices) + StatefulSets (MSSQL, RabbitMQ) + Ingress nginx avec TLS. ConfigMap ows-config (URLs internes *.ows.svc.cluster.local) + Secret pour mots de passe. Déploiement : kubectl apply -k k8s/. Cible HPA (Horizontal Pod Autoscaler) sur les microservices stateless.
CI/CD Pipelines basés sur les images Docker pré-buildées (${REGISTRY:-ows}/owspublicapi:${PLATFORM:-linux}-${TAG:-latest}). Health checks par service (bash -c 'exec 3<>/dev/tcp/127.0.0.1/80', interval 30 s). Variables d'environnement injectées via .env Docker Compose ou ConfigMap K8s.

Toutes les configurations critiques sont déclarées dans DefaultGame.ini sous la section [/Script/EngineSettings.GeneralProjectSettings] et lues via GConfig->GetString / GConfig->GetFloat au démarrage des composants OWS. Les secrets (OWSEncryptionKey, credentials) sont isolés dans DefaultGame_Secrets.ini exclu du contrôle de version.

OWSAPICustomerKey CustomerGUID unique de l'instance OWS du projet. Envoyé en header X-CustomerGUID sur toutes les requêtes API. Exemple : F9B16963-DC44-4E9C-9635-257FA18D4D41.
OWS2APIPath URL du microservice OWSPublicAPI. Dev : http://localhost:44302/. Prod : https://<serveur>/PublicAPI/.
OWS2InstanceManagementAPIPath URL du microservice OWSInstanceManagement. Dev : http://localhost:44328/.
OWS2CharacterPersistenceAPIPath URL du microservice OWSCharacterPersistence. Dev : http://localhost:44323/.
OWS2GlobalDataAPIPath URL du microservice OWSGlobalData. Dev : http://localhost:44325/.
OWS2APIRequestTimeout Timeout des requêtes HTTP en secondes. Défaut 30 s.
OWSEncryptionKey Clé AES-128 utilisée par UOWSGameInstance::EncryptWithAES pour chiffrer les coordonnées et données sensibles transitant par URL (?ID=...). Hashée MD5 avant chiffrement.
TravelTimeout / MaxRetryCount Timeout de voyage entre zones (60 s) et nombre de tentatives HTTP avant abandon (3, retry sur HTTP 5xx ou échec connexion ; pas de retry sur 4xx).

Sécurité — incohérences recensées

10 dettes connues · audits internes
Pour transparence — issues de sécurité documentées

Le backend OWS hérite de plusieurs issues de sécurité documentées par les audits internes (snapshot 2026-04-08). Aucune n'est bloquante en environnement de développement, mais leur résolution conditionne la mise en production. Liste extraite de OWS Architecture §"Incohérences de Sécurité".

#1 · Pas de validation propriété personnage Sévérité haute. Aucune vérification que le CharacterId demandé appartient à l'UserSession active — risque d'usurpation horizontal.
#2 · Header X-CustomGUID seul (pas JWT) Sévérité haute. L'authentification repose sur un seul header partagé. Pas de signature ni d'expiration. Cible : remplacement par JWT signé.
#3 · Rate limiting global (60 req/min) Sévérité moyenne. Limite trop laxiste, pas de différenciation par endpoint.
#4 · CORS AllowAnyHeader + AllowAnyMethod Sévérité haute. Configuration CORS trop permissive. À durcir.
#5 · HTTP inter-services (pas TLS) Sévérité moyenne. Communication entre microservices en clair — acceptable en réseau Docker isolé, à durcir en multi-noeud K8s.
#6 · RabbitMQ credentials par défaut Sévérité haute. guest/guest en config par défaut — à remplacer par credentials forts en prod.
#7 · Pas de versioning API (/v1/) Sévérité faible. Évolutivité limitée — toute breaking change cassera tous les clients.
#8 · Pas de correlation ID Sévérité faible. Tracing cross-service difficile sans ID corrélé. WithCorrelationId de Serilog présent mais pas propagé en HTTP.
#9 · Typo UserGu dans UserSessions Sévérité cosmétique. Nom de colonne mal orthographié — pas critique, à renommer en migration future.
#10 · Redondance CharHasItems vs CharInventoryItems Sévérité design. Deux tables stockent des items de personnages avec des sémantiques différentes (libre vs grille) — clarifier ou fusionner.
